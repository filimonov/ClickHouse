## Verdict

**Drop condition 1 (`current_catalog.etag == folded.catalog_cut->etag`). Keep conditions 2, 3 and 4. Scope a
row/life refusal to its namespace; keep a lease refusal, an unreadable catalog and an ambiguous cut as whole-pass stops.
Keep the fold's cut as the reference observation; a fresh cut at phase start is permitted, not required.**

- Q1: PROVEN for catalog independence. No reader of a life's `_log`/`_snap` objects takes any other namespace's
  catalog row as input. Every reader derives its start position from the life's own row (`ns`, `incarnation`), its own
  `_ckpt`, and its own `fold_seal.ref_lives[incarnation]` row. Condition 1 is a strict over-approximation of
  conditions 2+3. NOT claimed: that a reader holding an older `_ckpt` never meets a deleted object. That race exists
  today whenever cleanup runs, with a still catalog; dropping condition 1 makes cleanup run, so the race becomes
  frequent. Its outcome per reader is listed under Q1; one of them (fsck tail walk) is a false verdict.
- Q2: PROVEN SAFE to continue past a per-namespace refusal. The "refusal into a fallback" objection holds only for a
  shared licence; once each namespace is licensed by its own row there is no shared licence to weaken. Lease, catalog
  read failure and ambiguity remain whole-pass stops.
- Q3: The per-chunk predicate is PROVEN evaluable from durable inputs, given the round's `(lease.owner, lease.seq)`.
  `seq` is minted per round, so equality pins both the leader and the seal whose coverage row the executor used.
  Whether the round may clean at all is NOT durable today: `suppress_destructive` is computed in memory by the fold
  and is not in the seal. A multi-node coordinator must carry it. One ordering constraint for CAS-90 is named below.
- Q4: Keeping the fold's cut as reference and deleting only condition 1 is sufficient and is the minimal change. The
  "Review C3" hazard is real under the current name-keyed `folded.ref_tables` if a fresh read is used to RESOLVE the
  life; it is inert if a fresh read is used only to COMPARE the row. After B2 (per-life listing) resolution from a
  fresh cut is also safe.

## Failure asymmetry

| Option | How it fails | Cost |
|---|---|---|
| Keep condition 1 | Refuses every chunk whenever any namespace in the pool changed lifecycle state between the cut and the chunk; under DDL churn that is every round (46/46 stops locally, 0 deletes in 3 h on PR 2794 shard 2/2). | `_log` count of every long-lived namespace grows until restart; every recovery and every GC round lists all of it (CAS-432, CAS-447). Fails live, not safe: no data loss, unbounded cost. |
| Drop condition 1 wrongly | A chunk deletes a `_log`/`_snap` that some reader still needs. | That namespace's recovery throws `CORRUPTED_DATA` (`readCheckpointSnapshotBase`, `recoverRefTableDetailedFromAuthority`); the table is unreadable until repair. Irreversible. |

The burden is therefore on showing that no reader's inputs include another row. That is what Q1 does.

## Q1. Does any reader of a life's covered objects depend on another namespace's row?

### What the plan deletes

`Gc::cleanupRefObjects` (`CA/Gc/CasGc.cpp`) builds, per namespace in `folded.ref_tables`:

- `life = NamespaceLifeId::fromCatalogEntry(row.ns, row.incarnation)` from the fold's cut (`folded.catalog_cut`);
- `durable_cursor = folded.fold_seal.ref_lives[row.incarnation].coverage.last_folded_ref_id` (absent row: `{0,0}`, so no log is deletable; snapshots below the checkpoint stay deletable, as today);
- `checkpoint = folded.checkpoints[ns]` = this life's `_ckpt.checkpoint_snapshot_id`, validated as a triple by
  `readCheckpointSnapshotBase(op, layout, life, ckpt)`, which also returns `retained_log_proof`;
- `planRefCleanup(listing, durable_cursor, checkpoint, retained_log_proof)` (`CA/Pool/CasRefProtocol.cpp`):
  logs with `L <= durable_cursor && L < checkpoint && L != retained_log_proof`; snapshots with `S < checkpoint`.

Keys: `Layout::refLogKey`/`refSnapshotKey` (`CA/Formats/CasLayout.h`) are `cas/ns/stream/<incarnation>/_log|_snap/<id>`.
The key uses only `incarnation`; the name never enters a physical key.

None of these inputs is a function of another row: the seal row is keyed by incarnation and written by the intake from
this life's own stream and own `_ckpt` (`Gc::fold`, `cov.last_folded_ref_id = resolved_through`); `buildRefWalkPlan`
admits rows by incarnation and drops a parent row only when its own incarnation is absent from the cut;
`folded.checkpoints[ns]` is this life's own object (`readCheckpointWitnesses` enumerates witness keys per row, one
object each).

### How another row can touch this life at all

Only two ways, and both are already refused by conditions 2 and 3:

1. Rebirth of THIS name: the row's `incarnation` changes. Condition 2 (`*current_entry_it != observed_entry`).
2. Aliasing: another row admitted with THIS incarnation (keys use only the incarnation). Condition 3:
   `throwIfAmbiguous` throws on the re-read, `resolve(life.incarnation)` would not equal `life`. This is the case
   `684161dcc03` found when it narrowed the ref writer's check; the explicit ambiguity check closes it here too.

A CREATE, a DROP (`Live -> Removing`, row erase by `drainCompletedRemoving`), or a `Creating -> Live` of a DIFFERENT
name changes neither this life's `_ckpt`, nor its seal row, nor its stream. Uniqueness of names in the catalog
(`encodeRefCatalog` rejects duplicates) means no second row can carry this name.

### Readers that hold an older `_ckpt` (independent of condition 1)

A reader samples `_ckpt` (base `b`, frontier `f`), the writer then publishes checkpoint `c > b`, GC folds through it and
cleanup deletes logs in `(b, c)`. The reader then asks for one of them. No catalog row is involved, so condition 1
neither causes nor prevents this; it only kept cleanup from running. Outcome per reader:

| Reader | Outcome |
|---|---|
| Writer recovery (1) | 404, re-reads `_ckpt`, sees a different etag, restarts. Handled. |
| Periodic sweep view (4) | Ordered before cleanup within its own round. A sweep whose GC was deposed mid-round can meet a successor's cleanup: the view throws and that namespace's deletions are skipped. Fail-closed. |
| GC rebuild (5) | Cleanup by a PREDECESSOR leader was planned under a checkpoint `<=` the one rebuild samples, so it deletes nothing rebuild reads. A rebuild that is itself deposed mid-recovery can meet a successor's cleanup: recovery throws `CORRUPTED_DATA`, and its `gc/state` publication would lose the etag CAS anyway. Fail-closed. By argument, not tested. |
| Decommission sweep (15) | View throws, that namespace's deletions are skipped. Fail-closed. |
| fsck recovery leg (6) | `CORRUPTED_DATA` is caught and recorded `Unchecked`, unless the stream check before it already recorded chain-broken for the namespace; then chain-broken stays the verdict. |
| fsck tail walk (6) | Records chain-broken without re-reading `_ckpt`. FALSE VERDICT on a live pool. The base path in the same function already revalidates; the tail path needs the same. Follow-up, not a blocker for condition 1. |
| Inspect (14) | 404 for the operator. |

## Q2. Refusal scope

| Refusal | Scope | Reason |
|---|---|---|
| Own row absent, changed by value, or `resolve(incarnation) != life` | **This namespace only.** Stop its remaining chunks; continue with the next namespace. | Its keys are either dead-life debris (janitor's job) or belong to a row whose plan is stale and will be rebuilt next round. The other namespaces' licences do not take this row as input (Q1). |
| `gc/state` absent, or `lease.owner`/`lease.seq` moved | **Whole pass.** | The lease is the one shared licence: every post-CAS delete is an act of the leader of this round. A deposed leader must stop. Unchanged from today. |
| Catalog read throws | **Whole pass.** | No row can be verified; continuing would substitute "unverified" for "verified". |
| `throwIfAmbiguous` on the re-read | **Whole pass.** | Ambiguity is a corruption signal, not a churn signal; keep the pool-wide refusal `CatalogLifeIndex` documents for "destructive consumers". Narrowing to `isAmbiguous(life.incarnation)` would be correct but buys nothing measured. |
| Budget exhausted | Return, as today. | — |
| Recovery triple invalid | This namespace only, as today. | — |

On "continuing with another chunk would turn a refusal into a fallback": a fallback substitutes a different action
for the refused one on the same object. Skipping namespace A performs no action on A. Namespace B's chunk is licensed
by B's row, B's `_ckpt` and B's seal row, none of which A's refusal says anything about. The objection was correct when
one observation (the whole catalog) licensed all namespaces; after the change there is no shared licence except the
lease, and a lease refusal still stops everything. Two destructive paths already behave this way:
`excludeCandidatesWithChangedCatalogEntries` (per candidate) and the janitor (per key).

Within one namespace, a refusal must still stop that namespace's remaining chunks: the plan was computed from the old
row and a later chunk would delete under a stale life.

## Q3. Soundness without an in-memory cut (multi-node, spec section 7, CAS-90)

Durable inputs an executor needs for life X:

1. a catalog read taken by the executor: X's row must be `Live` or `Removing`, unambiguous, `resolve(incarnation) == (ns, incarnation)`;
2. `gc/state`: `snap_generation`, `snap_attempt`, and `lease.owner`/`lease.seq`;
3. the adopted seal `foldSealKey(snap_generation, snap_attempt)`: `ref_lives[incarnation].coverage.last_folded_ref_id` (absent row: no log deletable; an executor should delete nothing for such a life, which is stricter than today's planner);
4. X's `_ckpt`, validated through `readCheckpointSnapshotBase`;
5. X's own listing (B2).

Two inputs are missing relative to today. First, round eligibility: `cleanupRefObjects` returns at once when
`suppress_destructive` is set (anomalies, carried holds, incomplete frontier). The fold computes it in memory and the
seal does not store it, so an executor that sees a matching lease pair cannot tell an eligible round from a
suppressed one. The coordinator must either issue cleanup work only for eligible rounds or put the flag in the claim.
Second, the round identity the coordinator adopted: the executor must be handed
`(lease.owner, lease.seq)` of the round in its work claim and compare it to `gc/state` before each chunk. `seq` is
minted per round (`CasGc.cpp`: "every round mints a fresh `lease.seq` (= attempt)"), so equality pins the leader AND
the round, hence the seal whose coverage row was used. With both inputs the predicate below is evaluable from durable
state alone; no "moment of the fold" is needed, which is what section 7 constraint 3 asks for.

Ordering constraint for CAS-90, separate from the licence: cleanup of X must run only after this round's `gc/state`
CAS and after every pre-CAS protection walk that starts at the PARENT cursor (sweep, reader 4) has finished. In the
single-node round this holds by phase order (fold pre-CAS, cleanup phase 17). Multi-node must keep it with a barrier;
otherwise a sweep walking `(cursor_{N-1}, cursor_N]` races a cleanup deleting the same range. The decommission sweep
(reader 15) already runs outside this order and relies on its fail-closed handler instead.

## Q4. Reference cut

Required: the life, the cursor, the checkpoint and the listing must come from one observation keyed by
`incarnation`. Today that is the fold's cut plus `folded.fold_seal`, `folded.checkpoints`, `folded.ref_tables`.

The "Review C3" hazard is concrete under the current code: `folded.ref_tables` is `std::map<String, RefTableListing>`
keyed by NAME, and transaction ids restart at `{E,1}` per life. If cleanup re-resolved the name against a fresh cut
after a rebirth, it would pair the predecessor's listed ids and `_ckpt` with the successor's incarnation and could
delete the successor's `_snap` with an id below the predecessor's checkpoint. So:

- Fresh cut as the RESOLUTION source: unsafe before B2; safe after B2 (listing, cursor and `_ckpt` all keyed by the
  incarnation taken from that same fresh row).
- Fresh cut as the COMPARISON target only (life still from the fold's observation): safe now; it adds only the
  `Live -> Removing` case, which the next round handles anyway.
- Fold cut as reference, condition 1 dropped: safe now, minimal diff, independent of B2.

Recommendation: drop condition 1 now against the fold's cut. When B2 lands, the phase-start read becomes the single
observation naturally, because the fold-time listing disappears.

## Endorsed licence predicate

Per chunk of namespace X, with `observed_row` from the reference observation and `life = (X, observed_row.incarnation)`:

```
catalog   = read(cas/ref_catalog)              -- throws: stop pass
catalog.life_index.throwIfAmbiguous(...)       -- throws: stop pass
row       = catalog[X]
if row absent || row != observed_row || catalog.life_index.resolve(life.incarnation) != life:
    skip namespace X (its remaining chunks too); continue with the next namespace
state     = read(gc/state)                     -- absent: stop pass
if state.lease.owner != adopted.owner || state.lease.seq != adopted.seq:
    stop pass
delete chunk
```

Unchanged: the plan rule in `planRefCleanup`, the recovery-triple validation, the budget, post-CAS placement.

## Limits of what this establishes

- Established for `3fa3a01203b` of `antalya-26.8-pr-2159`. Line-level placement will drift; symbols are cited.
- The reader table covers every site that names `refLogKey`, `refSnapshotKey`, `namespaceStreamPrefix` or
  `casRefsPrefix` in `src/` outside tests, plus readers 14-16 found by review. A tool that mirrors or restores raw ledger objects is not in this
  worktree and is not covered. Note that a reader below the plan bound would already be broken by today's cleanup when the catalog is
  still; condition 1 only matters for a reader whose INPUTS include another row, and none of the enumerated readers has
  such an input. A future reader must take its positions from its own row, `_ckpt` and seal row to stay inside this
  argument.
- Cross-namespace atomic owner moves do not exist in this worktree: a `Move` is one op in one namespace's log,
  `moveRefExact` rejects different namespaces, and a cross-namespace `RENAME` is a re-drivable sequence of
  `republishRef` calls (`ContentAddressedTransaction.cpp`). A future two-log atomic move would need its own argument.
- Q3 is a soundness argument for the predicate, not a design of CAS-90. The barrier ordering above is a stated
  requirement, not verified against any multi-node code (there is none).
- Write settlement by a deposed writer (reader 16) was not traced: its late exact read of an id a successor has
  checkpointed past returns 404 once cleanup has run. No catalog row is an input, so condition 1 does not bear on it.
- Dropping condition 1 turns cleanup from almost-never into every eligible round. Every stale-`_ckpt` outcome in the Q1
  table then becomes routine. The fsck tail-walk false verdict should be fixed in the same release.
- Nothing was run. The refusal share after the change (AC #4) is a measurement for the CAS-29.7 counters.
- The verdict says nothing about LIST trust, the HEAD-before-PUT steps, new object kinds, or external deletion; all
  are out of scope by the dispatch.
