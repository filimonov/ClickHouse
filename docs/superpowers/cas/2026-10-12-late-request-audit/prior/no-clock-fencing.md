# Фенсинг зомби без часов: где безопасность CAS зависит от времени {#no-clock-fencing}

Код: `cas-janitor-budget` @ `3b4037ae265` (чтение через `git show`/`git grep`, без checkout). `CA/` =
`src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/`. Метки: **V** — проверено в коде или
документе (ссылка рядом), **I** — вывод, не проверенный тестом или моделью.

## 0. Вердикт {#verdict}

Гипотеза верна для ref-журнала и неверна для пула в целом.

- **Ref-журнал уже защищён без часов (V).** Запись в журнал — условный create по плотному ключу
  `(epoch, seq)`. Recovery преемника закрывает мёртвый epoch печатью `EpochSeal`, тоже условным
  create. Отставший append либо ложится до печати и принимается как законная запись, либо
  проигрывает печати (`CasRefLedger.cpp`, ветка `occupant_is_seal`/straggler в recovery-walk). Код
  говорит это прямо: старая пауза `materialization_grace_ms` удалена, потому что «the straggler's
  own conditional create loses to an occupied slot no matter when it arrives» (`Pool/CasPool.cpp:805`).
  Удаление манифестов зависит от печати, не от времени (`manifestDeletionPremise`, RULE 1,
  `Gc/CasOrphanManifestSweep.cpp:444`). Резерв `2 × конверт + запас` перед append (`refAppendFenceOk`)
  для самого журнала нужен только для живучести: без него неясный `PUT` у дедлайна оставит полосу в
  wedge без бюджета на разрешающее чтение (спека серии, §11, строка «Резерв в один запрос»).
- **GC печатать полосы не обязан (I).** Преемник печатает лениво, при первом обращении к таблице.
  Всё разрушающее, что касается epoch `E`, ждёт его печати. Печать силами GC дала бы только
  сборку мусора мёртвого epoch без преемника. Плата: O(namespaces) записей на фенс, GC становится
  писателем ref-журнала, а ложный фенс живого держателя превращается из «стоит один epoch» в
  `ledger_fault` → `std::terminate()`.
- **Гипотеза ломается на пяти классах записи и чтения.** Хранилище не может их зафенсить: ключ
  общий у зомби и преемника, а наблюдатель этот ключ не трогает. Либо запрос безусловный по смыслу.
  Классы перечислены в §3, и только для двух есть исправление без часов и без смены формата.
- **Что остаётся от времени после всех исправлений без часов.** Допуск держателя по остатку lease
  (не **отправлять** после дедлайна) и ожидание наблюдателя ≥ объявленного lease остаются для
  plain-объектов (`_files/`, `roots/<srid>/`). Без смены формата их не зафенсить. Остаётся и
  допущение «отправленный запрос применяется хранилищем не позже ~`конверт + запас + L/20 + шаг`
  после отправки» — то же самое, что сегодня, не слабее.

Итог: удалить резерв условной записи как **правило безопасности** можно для ref-журнала, `_ckpt`,
слота монтирования, счётчика epoch и манифестов. Удалить lease как механизм допуска нельзя, пока
plain-объекты пишутся вслепую. 17a/17b/18 нужны ровно для этого остатка.

## 3. Каталог записей зомби {#zombie-catalogue}

Зомби — процесс, поток или отправленный запрос, продолжающий действовать после того, как
наблюдатель решил, что держатель мёртв. Варианты: `SIGSTOP`/долгая пауза, сеть разорвана, запрос
отправлен до действия наблюдателя и применён после, второй экземпляр с тем же `srid`, и бывший
лидер GC.

**Поздний** — запрос, отправленный до фенса и применённый после. Для условного запроса условие
проверяется при применении. Значит, поздний условный запрос безвреден, **если наблюдатель меняет
целевой ключ**. На S3 ETag — MD5 содержимого, поэтому возврат к тем же байтам — это ABA
(spec 2026-09-30 §2.5).

| Z16 | второй экземпляр, тот же `uuid` и **тот же** epoch (потеря объекта счётчика) | два писателя одной полосы | предпосылка спеки §10, не фенсится | — | V (спека) |
| Z17 | вне CAS: ReplicatedMergeTree зомби с той же репликой в Keeper | действия реплики после отставки | сессия Keeper (таймаут — тоже часы) | — | I, не исследовано |

## 4. Предотвращение без часов по классам {#clock-free-prevention}

Ограничения хранилища: условие ставится только на целевой ключ; транзакций по нескольким объектам
нет; безусловные `PUT` и `DELETE` хранилище не фенсит. CAS требует нативного условного удаления и
проверяет его пробой (`ObjectStorageBackend::removeUnder` → `removeObjectIfTokenMatches`,
`NOT_IMPLEMENTED` — отказ). AWS S3 — ETag, GCS — generation, RustFS проходит пробу, Garage отвергнут
(`bucket-requirements.md`). Мутабельные объекты S3 с content-ETag подвержены ABA при возврате к тем
же байтам.

| # | Механизм без часов | Формат | Что остаётся от времени |
|---|---|---|---|
| Z1–Z4, Z10–Z14, G1–G7 | уже есть: плотные id + печать, epoch в ключе, условие на целевой ключ, exact-token удаление | достаточно | ничего для безопасности |
| Z6 | **CAS-334**: писатель никогда не превращает `Condemned` в `Clean` ни в одной из двух веток `reconcileMetaClean`; при конфликте — заново с `HEAD` и перепубликация. Маркер `Clean` тогда пишет только create после промаха, условием `If-None-Match` | без изменений (spec 2026-09-30 §10.2) | ничего; цена — лишние перезагрузки, пока GC не решит судьбу хеша |
| Z8 | relink-confirm `Yes` только после одного `GET` следующего id полосы `(E, T+1)` → `404`: пока печати нет, преемник не мог писать в эту таблицу (он пишет только после recovery с печатью), значит память зомби — вся история `E`. Ломает контракт «ноль I/O» | без изменений | ничего, если печать — единственный вход преемника (V для recovery-walk) |
| Z9 | то же для чтений, которым нужна свежесть; иначе — признать, что зомби отдаёт устаревшие чтения, как отстающая реплика | без изменений | — |
| Z7 | вариант A: преемник при первом обращении к таблице штампует свой epoch в строку каталога, сравнение зомби по значению падает. Вариант B: `RemoveNamespace` в журнал **до** перехода каталога (журнал зафенсен печатью) | A: новая семантика поля `creator` или новое поле — **смена формата**. B: протокол удаления меняется, нужна модель | без A или B — T1 |
| Z5 | условие на ключ, который наблюдатель меняет, требует, чтобы преемник переписал каждый `_files/<name>`. Переписать те же байты на S3 — тот же ETag (ABA). Тело — сырые байты без конверта, epoch-штамп некуда положить. Ключи по epoch требуют указателя по имени. **Без смены формата предотвращения без часов нет** | нужна смена формата (конверт с epoch или epoch-scoped ключи + указатель) | допуск держателя «не отправлять после `deadline − (E+M)`» + ожидание наблюдателя ≥ объявленного lease + допущение позднего применения |
| Z15 | recovery под живым epoch, встретив печать или запись другого epoch, — `ledger_fault` (CAS-351) | без изменений | ничего |

**Минимальное временное допущение, которое остаётся (Z5, Z7 без A/B):** запрос, отправленный
держателем не позже `deadline − (E + M)`, применяется хранилищем раньше, чем наблюдатель
действует: `deadline + L/20 + шаг` по часам наблюдателя (≈ `E + M + L/20 + шаг` = 7 + 2 + 1,5 +
10 ≈ 20 с для GC при значениях по умолчанию). Это то же допущение, что сегодня, оно не слабее.
Его по-прежнему держит неограниченная попытка (спека серии §4: per-socket таймауты,
`100-continue`, редиректы, DNS и учётные данные) — ровно то, что закрывают 17a/17b. Второе
допущение — расхождение хода `CLOCK_BOOTTIME` держателя и монотонных часов наблюдателя ≤ 5 %
(спека §10; остановленная ВМ — вне его).

Асимметрия отказа. Ложный фенс (наблюдатель поторопился) при защищённых хранилищем классах стоит
epoch. При Z5 он стоит потерянного обновления файла таблицы, при Z6 — висячего блоба. Поэтому
снять время там, где хранилище не фенсит, — путь отказа в сторону потери данных, а не задержки.

## 5. Остаточная схема {#residual-design}

1. Ref-журнал, `_ckpt`, снимки, манифесты, слот, счётчик, блобы, GC — без допуска по времени.
   Резерв `2E + M` перестаёт быть правилом безопасности. Для живучести хватает правила «нет
   неясного append без бюджета на разрешение», и оно не нужно, если чтения не гейтятся.
2. CAS-334 (Z6), relink-confirm с `GET (E, T+1)` (Z8), CAS-351 как `ledger_fault` (Z15) — без
   смены формата.
3. Plain-объекты (Z5) и, без варианта A/B, переходы каталога (Z7) остаются под одним
   временным допуском: «не отправлять после `deadline − (E+M)`». Один класс резерва вместо двух.
4. Наблюдатели (T3, T4, T6) остаются, пока жив пункт 3. Иначе это подсказка живучести.

Что это удаляет из серии:

| Механизм | Удаляется? |
|---|---|
| резерв условной записи `2E + M`, порог `paused/renewal_overdue` 14 с, второе неравенство `validateCasRequestBudget` | да, если Z5/Z7 переходят на однозапросный резерв `E + M` (пересчитать: plain-запись — RMW с разрешающим чтением) |
| резерв `E + M` и порог 21 с | **нет**, пока есть Z5 |
| пауза `lease_expired`, правило объявленного lease (PR 2), ожидание старта и `cas_unsafe_remount_no_delay` | **нет**, пока есть Z5 |
| 17a/17b/18 | **нет**: они закрывают именно допущение позднего применения для Z5/Z7 |
| получение заново (PR 14), классификатор потерь (PR 12) | нет, это не время |

Что добавляется: CAS-334, `GET` в relink-confirm, `ledger_fault` для CAS-351, расслоение допуска
по классам записи (тип операции плоскости, а не общий `writeLoop`), формат для Z5, если владелец
захочет удалить lease целиком. Печать полос силами GC **не** нужна (§0).

Формат: существующих типов записей хватает для пунктов 1–2. `EpochSeal` уже принимается recovery
от любого писателя. Для Z5 (и Z7-A) нужна смена формата, а формат заморожен с 26.6.4.

HEAD-before-PUT не трогается. CAS-334 меняет только решение после чтения `.meta`, не порядок
`HEAD` → публикация.

## 7. Что этот отчёт не устанавливает {#limits}

- Вред Z5/Z7/Z8/Z9 выведен из механизма, ни одного теста или трейса нет. Первым экспериментом
  стоит предсказание для Z5: зомби (`SIGSTOP` → reclaim преемника → `SIGCONT`) с отложенным
  `ALTER … DELETE` на не-replicated `MergeTree` перепишет `mutation_*.txt` преемника, если убрать T1.
  Его не запускали.
- Порядок «тело манифеста до precommit» взят из документа (`manifests-and-refs.md`), в
  `CasPartWriteTxn.cpp` построчно не проверен.
- Код вне `CA/` не смотрели: Poco/S3-клиент (где на самом деле ограничена попытка), Keeper/RMT
  (Z17), `DataPartsExchange.cpp`.
- Утверждение «GC-зомби безопасен» опирается на документ и названные модели. Удаления GC
  повторно не проверялись, кроме `removeUnder` и `writeCondemnedMeta`.
- Утверждения о провайдерах (AWS/GCS) взяты из `bucket-requirements.md` и пробы, а не из
  документации провайдеров.
- Полнота §2 — по источникам часов в `CA/`. Решения по времени в вызывающем коде MergeTree не
  входят.
