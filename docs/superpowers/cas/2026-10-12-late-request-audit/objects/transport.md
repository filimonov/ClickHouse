# Аудит `transport`: время одного запроса CAS от допуска до эффекта в хранилище {#transport-audit}

База `d76b59f9295` (`cas-janitor-budget`). `CA/` = `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/`.
**V** — прослежено в коде базы (`файл:функция`); **I** — вывод (код не исполнялся; поведение ядра/OpenSSL/хранилища — общее знание).
Умолчания: `L`=30 с, `P`=10 с, `T`=5 с (`attempt_timeout_ms`), `C`=1 с (`connect_timeout_cap_ms`), `M`=2 с; `E = T+2C` = 7 с.
Объект аудита сквозной: вместо «одного объекта» — путь одного запроса. Разделы брифа переложены так: §1 путь, §2 профили, §3 сценарии, §4 строгость, §5 таймауты + оценка «дедлайн в транспорте», §6 перенос на хранилище, §7 ZooKeeper, §8 TLA+, §9 вывод.

## 3. Сценарии {#scenarios}

«Окно наблюдателя» — сколько наблюдатель ждёт после первого наблюдения неизменного токена слота: GC `1,05L + P` = 41,5 с, re-mount `1,05L + P/2` = 36,5 с. Последний допуск записи у держателя — при `remaining = 16 с`, то есть за 16 с до `deadline`.

Значит пул не может «отложить» запрос на другое соединение (V).

## 4. Нужная строгость {#strictness}

- Худший вред транспортного опоздания — не свой: перезапись общего пути (`_files/`, `roots/`) поверх преемника (T3) и удаление живого блоба точным токеном (T1). Это потеря данных.
- TR2, TR3, TR4, TR5, TR7 — у исправного хранилища редки: нужен ответ, капающий у границы аренды. Но они ломают единственное утверждение, на котором стоит резерв `2E+M`: «попытка ≤ E». Поведение уже наблюдалось: медленный `PUT` продления, 6 с в `finalize` (CAS-353 в спеке серии).
- TR1 и TR9 требуют паузы или разрыва > 16 с + окно. Пауза SIGSTOP/своп/live-migration редка; разрыв сети с последующей ретрансляцией — обычный случай.
- «Минимизировать и обнаруживать» допустимо для TR2–TR7 (время), если для объектов, где хранилище не фенсит, есть детектор. Для TR1/TR9/TR10 на общих путях транспорт дать «невозможно» не может (раздел 5.4) — только хранилище (раздел 6).

## 5. Таймауты и дедлайн в транспорте {#transport-deadline}

### 5.1. Что ограничено сегодня {#bounded-today}

| Запрос | Ограничено | Не ограничено |
|---|---|---|
| условный `PUT` | каждая операция сокета ≤ `T`; connect/TLS ≤ `C` каждый; первая попытка — адаптивно; повторы SDK = 0 | число операций; редиректы ×11 (×2 цикла); повтор первой записи; `100-continue` + тело; DNS; учётные данные; ограничитель; хвост в буфере ядра; применение хранилищем |
| `GET`/`HEAD`/`LIST`/`DELETE` | то же | то же, кроме тела запроса |
| multipart условный | каждая часть — как `PUT` | число частей под одним резервом |
| `publish` | `requestTimeoutMs` = 30 с на операцию | 500 повторов, буферный цикл 4, multipart |

Итог: «конверт» `E` — оценка, не граница. Спека серии говорит то же (`docs/superpowers/specs/2026-10-07-cas-mount-lease-series-design.md`, раздел 4).

### 5.2. Предложение {#proposal}

Одно атомарное `lease_valid_until`, продлеваемое продлением; перед каждой операцией сокета проверка; таймаут сокета = `min(настроенный, remaining − M)`; обрыв соединения на границе.

`lease_valid_until` уже есть: `mount_fence.deadline_boot_ms` (`std::atomic`, `CLOCK_BOOTTIME`), пишется в `consumeRenewResult`, читается в `CasMountRuntime::admit` (V). Новое — только доставка до сокета.

Ключевое наблюдение: для безопасности важен один момент — **уход последнего байта запроса**. До него хранилище запрос не применит (неполное тело, I); после — обрыв не отменяет. Отсюда классы точек:

| Точка | Безопасность | Живучесть |
|---|---|---|
| DNS, учётные данные, connect, TLS, сон ограничителя | нет: ни один байт запроса не ушёл. Нужна только перепроверка **после** них | да: ограничивают задержку ответа |
| каждый `send` заголовков и тела | **да**: проверка `now < until − M` до операции, таймаут ≤ остатка | да |
| `peek` `100-continue`, `recv` ответа | нет: последний байт уже ушёл либо тело не будет отправлено | да: раньше узнать исход, раньше разрешить неясность |
| закрытие при обрыве | **да**: без `SO_LINGER{1,0}` хвост тела уйдёт после обрыва (TR10) | — |
| ретрансляция ядра | **да**: без `TCP_USER_TIMEOUT ≤ остатка` ядро допошлёт буфер после разрыва (TR9) | — |

### 5.3. Куда встроить {#hook-points}

Ограничения варианта (I, проверить):
- thread-local работает только на потоке вызова. Условные записи — да (`s3_allow_parallel_part_upload = false`, V). `publish` с параллельными частями и `stream` (тело читается позже потребителем) — нет: нужен явный канал через `WriteSettings`/`ReadSettings`, как `object_storage_attempt_number`. Номер попытки едет заголовком `clickhouse-request` (`src/IO/S3/Requests.cpp:setClickhouseAttemptNumber`), дедлайну так нельзя — нужен указатель, не значение.
- `setTimeout` на подключённой сессии делает `setsockopt` только при изменении значения (`HTTPSession::setTimeout`, V) — до двух системных вызовов на операцию.
- TLS: `SecureSocketImpl::getMaxTimeoutOrLimit` берёт таймауты нижнего сокета (V); комментарий `FIXME` в `SecureSocketImpl::connect` говорит, что таймауты обёртки и нижнего сокета расходятся — проверить, что `setTimeout` сессии доходит до `SSL_write`.
- `TCP_USER_TIMEOUT` — только Linux.

Сцепление с апстримом: `PocoHTTPClient.cpp`, `HTTPConnectionPool.cpp` — общий код всех S3-дисков. Механизм нейтральный («общий дедлайн запроса»), без полей CAS; включается только при установленной области. Спека серии отложила это как 17b (решение владельца 2026-10-08).

### 5.4. Что закрывает и что остаётся {#closes}

| Сценарий | После дедлайна в транспорте | Почему |
|---|---|---|
| TR2, TR3, TR5, TR6, TR7 | **закрыт** | каждый `send` после `until − M` отказан; редиректы и повторы проходят ту же точку |
| TR4 | **закрыт** по времени | повторная подпись — новый `send` |
| TR8 | закрыт по времени, если `publish` получит дедлайн явным каналом | 500 повторов упираются в `until − M`; семантика T1 (тот же content-ETag) остаётся |
| TR9 | закрыт с `TCP_USER_TIMEOUT` | ядро сбросит соединение с неподтверждёнными данными |
| TR10 | закрыт с `SO_LINGER{1,0}` | `RST` отбрасывает буфер |
| TR13, TR14 | безопасность и так не задета; живучесть — перепроверка после | — |
| **TR1** | **открыт** | проверка и `send` — две инструкции; пауза между ними не видна. Допущение: пауза ≤ запаса |
| **TR11** | открыт | прокси подтвердил TCP; `TCP_USER_TIMEOUT` не помогает |
| **TR12** | открыт | применение после последнего байта |
| TR9 частично | открыт, если ядро держатель паузит вместе с процессом (VM) | таймеры ядра стоят вместе с гостем |

Запас для оставшихся допущений: последний байт держателя ≤ `until − M` = `start + 28 с` (часы держателя). Наблюдатель действует ≥ `sighting + 1,05L + P` ≥ `start + 41,5 с` (свои часы). Запас ≈ `M + P` = 12 с для GC, `M + P/2` = 7 с для re-mount, минус расхождение хода часов ≤ 5 % (I). В этот запас должны уложиться TR1 (пауза после проверки), TR11, TR12.

### 5.5. Что можно удалить {#deletable}

| Механизм | Сейчас | После | V/I |
|---|---|---|---|
| конверт `E = T + 2C` (`CasRequestBudget::attemptEnvelopeMs`) как единица резерва | основа допуска | не нужен для безопасности; остаётся как оценка живучести (сколько закладывать на разрешение неясности) | V (код), I |
| резерв `2E + M` / `E + M` в `gate` | правило безопасности | правило живучести: «не начинать запись, которую нечем разрешить». Безопасность держит `M` в транспорте. Можно опустить до `M + p99` → записи до `start + ~27 с` вместо `+14 с` | I |
| `validateCasRequestBudget` | две проверки: `E + M < L`, `P + 2E + M < L` | остаётся `P + M < L` (и `M > 0`) | V/I |
| `connect_timeout_cap_ms`, заморозка капа, `ensureBackendMatchesBudget` | держат `E` честным при перезагрузке клиента | не нужны: транспорт режет остатком | V/I |
| ключ кеша клонов `(T, C)` в `getSingleAttemptClient` | — | клон нужен только ради `max_retries = 0`; ключ упрощается | V |
| пер-вызовные бюджеты (`Retry::untilLeaseSafe`, `fits` с `lease_bound`) | граница политики + аренды | граница политики остаётся (живучесть); `lease_bound` — лишний | I |
| `AdmittedBodyReadBuffer` | гейт refill | остаётся: чтения не про безопасность записи, но потерянный fence должен останавливать | V |
| окна наблюдателя `1,05L + P` | — | **не меняются**: наблюдатель ждёт аренду держателя на своих часах | I |

Удаляется резерв, не наблюдатели. Наблюдатели (T3/T4 в `inventory.md`) нужны, пока есть объекты, которые хранилище не фенсит.

## 6. Перенос гарантии на хранилище {#store-level}

Транспорт делает допущение «запрос не позже `until − M`» правдой с точностью до TR1/TR11/TR12. Хранилище может сделать опоздание безвредным только там, где запрос условен на то, что меняет преемник.

| Вариант | Что | Формат | Объём | Риск |
|---|---|---|---|---|
| A. Ничего в транспорте, всё в хранилище | эпоха в ключе или в конверте для общих путей (T3), CAS-334 для `.meta` (T2) | меняет (FROZEN с 26.6.4) — см. аудиты объектов | большой | миграция |
| B. Дедлайн в транспорте (5.3) | закрывает TR2–TR10 по времени | не меняет | ~170 строк, 4–5 файлов общего кода | апстрим-сцепление; TLS-таймауты проверить |
| C. Оставить + контроль | счётчики: попытка дольше `E` (гистограмма `S3FirstByte`/`DiskS3*` уже есть, нет метрики «последний байт после `until − M`»); `CASRequestFenceLostPostWrite` (V) ловит только исход после потери fence | не меняет | ~30 строк | вред обнаруживается после факта |

Минимальный детектор для C: в send-хуке не обрывать, а считать `CASTransportSendAfterDeadline` (байт ушёл при `now ≥ until − M`). Это та же точка, что в B.

## 7. Сравнение с сессией ZooKeeper {#zookeeper}

| ZooKeeper (Curator) | CAS сегодня | CAS с дедлайном в транспорте |
|---|---|---|
| **Live**: сессия жива, операции идут | `Admit::Ok` | то же |
| **Suspended**: связь потеряна, исход сессии неизвестен; операции падают `ConnectionLoss` (повторяемо); лидер обязан прекратить лидерские действия | `Admit::NoBudget` → `GaveUp{Deadline, Lease}` / `throwCasWriteRetryLater` (повторяемо) — V | то же, плюс в полёте: запрос, пересёкший `until − M`, обрывается и даёт `Unresolved` |
| **Lost/Expired**: сервер закрыл сессию; эфемерные узлы удалены; нужна новая сессия | `Admit::LostOrRearmed` (`tripMountLost`, рост `fence_generation`) | то же |
| Возобновление той же сессии: переподключение до истечения на сервере | продление после `deadline` с той же эпохой проходит, если токен слота не менялся (TR17, `CaCasMountCoreLateRenew`) | то же |
| Кто решает «истекла»: **сервер**, по своим часам; клиентские часы — лишь подсказка | наблюдатель на своих часах (`computeHeartbeatFloor`, `claimMountAwaitingExpiry`) + токен слота как арбитр | то же |
| Поздний запрос истёкшей сессии: **сервер отклоняет**, каждая операция несёт `session_id`, применение в порядке FIFO одного соединения | отклоняется только запрос, условный на ключ, который сменил наблюдатель/преемник (`If-Match` на слот, эпоха в ключе). Остальные — по времени | то же; время теперь честное, кроме TR1/TR11/TR12 |

Главная разница — не в состояниях, а в арбитре. У ZooKeeper сервер проверяет сессию при **применении** каждой операции. У S3 условие — только на один ключ запроса. Поэтому семантика ZooKeeper полностью достижима лишь для записей, условных на ключ, который меняет фенс. Для остальных переход Suspended → Lost у CAS — по часам, и дедлайн в транспорте лишь делает эти часы правдой на стороне отправки.

Уточнение к состояниям: в Curator Suspended вводится по событию связи, не по часам. В CAS Suspended = «остаток < резерва» — по часам держателя. С дедлайном в транспорте Suspended наступает при `remaining ≤ M` (резерв живучести можно оставить отдельным порогом приёма новых операций).

## 8. TLA+ {#tla}

| Модель / оператор | Что покрывает | Чего нет |
|---|---|---|
| `CaMountObserveCore`: `Write`, `NoWriteAfterFence`, `FenceMarginAtLeast`, `NoFenceInsideAuthority` | допуск записи при `hclock < AuthorityEnd`; фенс наблюдателя после `Threshold` | `Write` атомарен: допуск = применение. Длительность в полёте, TR1–TR12 не моделируются; запас `MinMargin` — единственное место, куда они «помещаются» |
| `CaCasMountCore`: `StragglerLands`, `WedgeAdmit`, `WedgeRetryCreate`; обёртка `CaCasMountCoreStraggler` | поздняя adopt-запись под защёлкой fence | только объект слота (условный); общих путей нет |
| `CaCasMountCoreLateRenew`: `RenewAfterExpiry`, `LaneRetriesAfterRenew` | TR17: продление после истечения той же эпохой, полоса продолжает | — |
| `CaMountRenewRetryCore` | повторы продления, неясные исходы | транспорт внутри попытки |

Минимальное дополнение: в `CaMountObserveCore` разделить `Write` на `WriteAdmit` (проверка `hclock < AuthorityEnd − Margin`, переменная `inflight` с моментом допуска) и `WriteLand` (в любой момент, пока `hclock ≤ admitTime + MaxFlight`, где `MaxFlight` = 0 для варианта B и ∞ сегодня). Свойство: `WriteLand` не после `slotFenced` для объекта без условия. Ожидаемо: при `MaxFlight = ∞` — контрпример (сегодня); при `MaxFlight ≤ Margin + Cadence` — зелено. ~40 строк, 1 cfg на значение. Паузу TR1 моделирует то же `MaxFlight`.

## 9. Вывод {#verdict}

- Сегодня: **safe-by-time только на бумаге**. Резерв `2E + M` предполагает «попытка ≤ E», а транспорт ограничивает операцию сокета, не попытку: капающий ответ, `100-continue`, multipart до 18 запросов, 11+11 редиректов, `publish` с 500 повторами, хвост буфера ядра после обрыва (V).
- Дедлайн в транспорте (send-хук + `SO_LINGER{1,0}` + `TCP_USER_TIMEOUT` + область на потоке вызова; ~170 строк в `src/`, без `base/poco`) делает эту границу правдой для TR2–TR10 и позволяет удалить конверт `E`, две проверки `validateCasRequestBudget`, кап connect и `lease_bound`. Окна наблюдателей не меняются.
- Остаются три допущения в запасе ≈ `M + P` (12 с GC) / `M + P/2` (7 с re-mount): пауза между проверкой и `send` (TR1), прокси с буфером (TR11), позднее применение хранилищем (TR12).
- Рекомендация: сделать 17b в форме 5.3 (сначала детектор `CASTransportSendAfterDeadline`, затем обрыв), безопасность общих путей — только хранилищем (раздел 6, аудиты T1/T3). Модель: разделить `Write` в `CaMountObserveCore`.
