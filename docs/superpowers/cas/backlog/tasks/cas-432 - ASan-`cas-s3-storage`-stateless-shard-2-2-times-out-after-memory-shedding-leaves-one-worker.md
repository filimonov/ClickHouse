## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`Stateless tests (amd_asan_ubsan, cas s3 storage, parallel, 2/2)` hit the 12600 s job timeout on https://github.com/Altinity/ClickHouse/pull/2704 (head feefeca33d8, run 41807147619) with 2860 of 6929 tests done. The lane ran for the first time on a pull request there (before feefeca33d8 the CAS stateless lanes were deferred behind the core blocking jobs and skipped). Evidence in the job log (master/tmp/pr2704/asan22/job.clean.log): between 10:00:37 and 10:10:00 UTC `clickhouse-test` printed `Server memory at 80% of limit — signalling one worker to stop after its current test` seven times, tracked workers went 8 → 1, and nothing restores them; the per-test median stayed 3 s, so the pace fell eightfold (62-97 tests per 10 min against 500-640 in shard 1/2, which never shed a worker and finished 6889 tests in 117 min). `--memory-limit 10737418240` (10 GiB).

Unknown: whether the server really held 8 GiB (CAS ledger state, caches, ASan quarantine) or a few tests in shard 2 (for example `03748_join_on_complex_condition_result_memory`, 143 s there) pushed it over the threshold once. No server log survives a timeout.

Options, cheapest first: (a) three or four batches for the ASan CAS S3 lane, as the MSan lane already has three (ci/defs/altinity_jobs.py); (b) a higher memory limit for the ASan CAS lanes; (c) a server-log capture on timeout so the next occurrence shows what held the memory. Pick after one measured rerun with memory metrics.

Shedding cannot lower this RSS: at the threshold MemoryTracking was 0.4-1.5 GiB and the rest is ASan runtime - /proc/pid/smaps: ~6 GiB fake stacks (detect_stack_use_after_return, one 11.1 MiB mapping per thread, ~7 MiB touched), ~2.6 GiB 8 MiB thread stacks, ~6 GiB ASan allocator regions, ~4 GiB other anonymous, 2 GiB shadow, 1.5 GiB binary; corr(threads, RSS)=0.87 at ~15 MiB per thread, 1237 threads (max_thread_pool_free_size default 1000 keeps idle threads and their fake stacks). 26.6 vs 26.8: same compiler-rt flag defaults and same ASan default options apart from allocator_may_return_null; the 26.8 lane runs 21 percent more tests (14485 vs 11996 files in 0_stateless) and 25 percent slower per test; 26.6 shard 2/2 peaked at 20.8 GiB (MemoryWorker resident), 26.8 shard 1/2 at 17.9, shard 2/2 crosses 22. Root cause: clickhouse-test judges memory pressure by server RSS (comment in get_server_memory_fraction says MemoryTracking under-reports under sanitizers), but under ASan RSS is dominated by per-thread runtime state that shedding clients does not release, and the shed is irreversible, so the shard drains to one worker and hits the 12600 s limit. Fix options, in order of cost: (1) run the ASan cas-s3 lane with ASAN_OPTIONS detect_stack_use_after_return=0 or max_uar_stack_size_log=16 (cuts the ~6 GiB fake stacks; upstream CI does not set it either); (2) make the shedding reversible or base it on MemoryTracking plus a hard RSS guard near the OOM line; (3) lower max_thread_pool_free_size for sanitizer runs; (4) larger runner. 2026-11-11 RCA of the in-run slowdown (why 41d4a78eeb9 went 1325 -> 520 tests per 30 min without shedding). Data: PR 2794 shard 2/2 metric_log, the only timed-out cas-s3 run that uploaded one (tmp/lanes/ci/pr2794_2_2_artifacts, q2-q7.sql), job logs of 2792/2794/2799/2805/2808/2810 and the 26.6 lanes (tmp/lanes/ci/lane_rca2.py), plain-ASan master run ab9c400, and a synthetic RustFS benchmark (antalya-26.8-pr-2159/tmp/cas432/rustfs_bench/{bench.py,bench2.py,result.tsv,result2.tsv}). Two effects stack. (E1) Runner variance: the same commit on the same day ran 1.6x slower on one AMD_LARGE runner than on another (PR 2808 shard 1/2 vs 2/2). (E2) A progressive slowdown inside every cas-s3 run on both branches: test wall time relative to the binary cas-s3 lane grows from 3.8x at the start to 6.6-7x after 2.5 h on 26.8 (2799: 3.8->6.7, 2810: 3.9->6.6, 2808 2/2: 4.4->7.0) and to 6.0-6.7x on 26.6; the plain ASan lane without CAS on the same runner type grows only 4.1->5.0. Short tests (2-5 s) slow the most (x1.36 -> x1.95); workers stay fully busy (~14400 worker-seconds per 30 min bucket), no shedding, identical clickhouse-test command line, same 4.5 min startup. Where the time goes (2794 2/2, 10-min buckets, 13:10 -> 15:30 UTC): server CPU flat at 3-4 of 16 cores, OSCPUWait ~1 core, IOWait 0, MemoryTracking <= 1.3 GiB, ContextLock/RWLock waits negligible, no S3 throttler sleeps, ~30 new HTTP connections per 20 min. The S3 request rate stays ~450-480 req/s while the query rate halves, and the server-measured per-request latency grows: HEAD 2.5 -> 14.5 ms, LIST 14 -> 58 ms, GET 1.5 -> 5 ms, PUT 4.9 -> 8.8 ms; summed S3 wait per query 0.11 -> 0.32 s, query time per query 0.21 -> 0.61 s; GlobalThreadActive 636 -> 1084 with fewer queries (threads blocked in S3 calls). The bucket receives 1.3M PutObject and ~0.37M deletes over the run, ~1M objects at the end. RustFS 1.0.0-rc.3 benchmark (same env vars as ci/jobs/scripts/clickhouse_proc.py, 1 KiB objects in the CAS key layout, 16 client threads): HEAD/GET/PUT/DELETE latency does NOT depend on the object count (HEAD p50 9.9-11.9 ms from 100k to 1M objects, PUT 17.5-20.4 ms), so the bucket size alone is not the cause; LIST costs ~0.15 ms per RETURNED key (3 ms empty, 56 ms for ~390 keys, 148 ms for 1000 keys, 200+ ms at 800k+ objects). bench2 on the filled bucket: 8 threads of HEAD+GET alone: p50 5.6 ms, p95 18 ms, 562 ops/s; with 4 background LIST threads (14.5 LIST/s of 1000 keys, i.e. the CI rate): p50 13.3 ms, p95 50 ms, 221 ops/s (2.4x slower, 2.5x less throughput); back to 5.6 ms / 563 ops/s when the LISTs stop. ROOT CAUSE: RustFS serves LIST by reading per-key metadata, and the server issues 10-15 LIST/s whose result sets grow over the run (every table open/recovery lists its ledger _log prefix, GC enumerates cas/ns/stream/ every 20 s, part-folder listings go to cas/roots/); the growing LIST work starves the HEAD/GET/PUT data path for all 8 workers, so every test waits longer on S3 the longer the run is. Why the ASan lane suffers most: it runs 3-3.5 h per shard (the binary lane 57 min), so the LIST result sets have more time to grow, and its per-test S3 wait is a bigger share because the CPU part is slow too. Why the ledger listings grow: CASRefCleanupObjectsDeleted stayed 0 for the whole 3 h while ~180k _log objects were published (one per CASRefBatchFlushes); see CAS-447. Fix directions: (1) make ref-log cleanup actually run (CAS-447), which bounds the _log listings; (2) 3 shards for the ASan cas-s3 lane as a budget measure independent of (1); (3) optional: cap GC enumeration rate for test configs (cas_gc_interval_sec 20 is 90 enumerations of cas/ns/stream/ per 20 min).
