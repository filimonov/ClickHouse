# CAS Backlog — Formats and storage backends {#formats-and-storage}

Part of the [CAS live backlog](/superpowers/cas/backlog). Topic file for format-compatibility and
codec items, manifest/blob and ref-ledger/GC object items, and backend (S3/GCS/POSIX/emulated) items.

## Format compatibility (frozen since 26.6.4) {#format-compatibility}

The on-S3 format is FROZEN as of `26.6.4.20001.altinityantalya` (user decision, 2026-09-25). Every
item below that would change wire bytes or reinterpret an already-persisted object needs a format
version and a compatibility path before it can land; a behavior-only fix (validation, bounds,
observability) does not. Items are annotated individually where this applies.

- **[cas-format-version-floor] `checkCompatibility` never rejects a version below a type's own birth generation** — {#cas-format-version-floor} — DESIRABLE — `checkCompatibility` (`Formats/CasFormat.cpp:72-77`) throws `UNKNOWN_FORMAT_VERSION` above `G_BUILD` but accepts anything below it, including a version under the type's own birth generation (e.g. a header claiming generation 1 for a type born at generation 4 decodes as legal); `decodeRefCatalog` also discards the parsed header once the check passes, so nothing downstream can recover the version for logging. Not required by the empty-universe GC gate fix that surfaced it — closing this floor would only shrink an already-accepted residual, not remove it. Fix: a per-type birth-generation floor enforced centrally in `checkCompatibility`, refusing a version below `changePoints(id).front().generation` as `CORRUPTED_DATA`; blast radius is the shared format layer used by every CAS object type, so needs its own failing-first coverage and a fixture/artifact audit. The floor check itself is behavior-only (rejects what should already be invalid), but if the fix also changes how a below-floor version is reported or recovered, verify it against the freeze rule.
- **[codecs.md standardization]** — DOC (proposed) — Complete the magic table (`OwnerProto`/`ServerEpochProto`/`MountLeaseProto`/`FoldSealProto`); decide the `RunRef.checksum` / `PartManifest.payload_digest` CRC-boundary before release. No `docs/superpowers/cas/codecs.md` exists yet. The earlier "standardize binary version fields (`compatibility_version` vs local `format_version`)" bullet is dropped: the `RunFile` format it targeted was deleted (formats v3, see below), and `PartManifest` shows no competing local field — grep for `format_version`/`compatibility_version` literals in `Formats/CasPartManifestFormat.*` turns up nothing, it already uses the shared `compatibility_version` mechanism. Any magic-table entry that documents a wire byte layout is definitionally about the frozen format — this doc is where the "needs a version + compat path" note belongs for future changes, not a trigger for one itself.
- **[gc-snap-codec-tlv-review] B176 format-freeze review of the `gc/snap` streamed codec's envelope TLV fields** — DESIRABLE — Concrete review action item ahead of the format-freeze gate; still unreviewed.
- **[SEAL-DECODE-REMAINING-FIELDS] ✅ CLOSED at HEAD by `2bbcbb1868313b0f3d9924054bb2141928b7a0f9`** — {#seal-decode-remaining-fields} — was SMALL FOLLOW-UP (2026-07-29, T16 concern 2) — the fold-seal codec's ref-life hold/cleanup-evidence fields (originally named `btr`/`cnd` before the wire-keys semantic rename) now refuse an incomplete record as `CORRUPTED_DATA` instead of silently defaulting; verified against current `Formats/CasFoldSealFormat.cpp` (hold-field completeness ~lines 480-500, cleanup-evidence completeness ~505-517). The wire-key semantic rename (`d73a13e1bf7a` "cas: cut cas_run row keys to semantic names") replaced the original short field names with `shard`/`generation`/`checksum` etc.; the closure itself is unaffected. Kept for provenance only.

## Manifests and blobs {#manifests-and-blobs}

- **[manifest-inline-budget-no-spill] The 16 MiB per-manifest inline budget has no re-classification path (2031-triage CAS-044)** — {#manifest-inline-budget-no-spill} — `PartWriteTxn::stageManifest` enforces three fail-closed caps (`Pool/CasPartWriteTxn.cpp:596-614`): `kMaxManifestEntries`, the per-entry `kMaxLargestInlineEntryBytes = 1 MiB`, and the aggregate `kMaxManifestInlineBytesTotal = 16 MiB` (`:55-57`). The per-entry cap has a spill path — an inline candidate above `INLINE_CAP = 1 MiB` is written to a local temp file and staged as an ordinary blob (`ContentAddressedTransaction.cpp:932-970`) — but the aggregate cap has none: nothing tracks a running inline total while files are staged, and `stageManifest` cannot re-place an entry, so a part whose inline-eligible files sum past 16 MiB throws `LIMIT_EXCEEDED` and the INSERT (or the merge that would produce that part, or a repoint through the same call) fails permanently and reproducibly for that schema/data shape.

  Reachability is wider than "many projections or skip indexes" suggests, because the inline-candidate set is the complement of the `partFileMustStayBlob` allowlist (`ContentAddressedTransaction.cpp:65-73`) and that allowlist misses the shipped default names (see [`part-file-suffix-allowlist-memory`](performance.md#part-file-suffix-allowlist-memory) below): `primary.cidx`, `.cmrk4` (compact-part marks with substreams), every skip-index `.idx`, and — because the `primary.idx` branch is an exact-name compare — every projection's `<proj>.proj/primary.idx`. Projection files live in the PARENT part's manifest, so ~8-17 near-1-MiB files across a handful of projections reach the aggregate cap while each stays under the per-entry cap that would have spilled it.

  Loudness: fail-closed and loud (`LIMIT_EXCEEDED` before the body PUT and before `uploadPendingBlobs`) — no corruption, no partial publication, only local scratch work wasted. Hence P2, not a release blocker; the failure mode is a table whose parts can never be written, discovered at the first INSERT.

  Owed: track the inline total during staging and demote the largest inline candidates to blobs before the cap (the machinery already exists on the per-entry path), so the cap becomes a placement decision instead of a write refusal. Fixing [`part-file-suffix-allowlist-memory`](performance.md#part-file-suffix-allowlist-memory) shrinks the exposure but does not close it (projection metadata and skip-index bodies stay inline-eligible by design). Behavior-only fix, no wire-format change.

- **[write-once-probe-misses-multipart] Write-once probes and multipart blob publication (2031-triage CAS-031)** — {#write-once-probe-misses-multipart} — **CLOSED for blobs by the 2026-08-23 protocol rewrite; identifier kept for provenance.** Blob-body PUT/copy no longer carries a destination precondition and therefore no longer asks a small write-once probe to certify multipart behavior — confirmed via `checkConditionalWriteSingleAttemptSupport` (`Backend/CasObjectStorageBackend.cpp:199`, a MOUNT-TIME gate) and the comment at `:801-802` ("Blob publication never uses these settings; it remains an ordinary unconditional multipart-capable write"). Streaming bodies use ordinary multipart; explicit S3 staging requires native same-store copy and fails closed when that capability is absent. The conditional capability battery remains load-bearing for small mutable metadata/control objects, native-token `HEAD`, and exact deletion, none of which delegates a blob-body multipart contract to the probe. Related LIST trust work remains tracked at {#list-consistency-real-s3}.

- **[skip-access-check-no-signal] `skip_access_check` and the decommission open silently skip the whole probe (2031-triage CAS-030)** — {#skip-access-check-no-signal} — Confirmed unchanged: `skip_access_check` (`Pool/CasPool.cpp:481,505-507,917`) still skips the capability probe wholesale, and `clickhouse-disks cas-drop-member` opens read-only, which never probes at all — so `openForDecommission`'s comment ("the calling disk validated it") does not hold for capability in that path. Not the "removes every bucket defense" an earlier audit claimed: the single-attempt gate and the residual proof stay (deliberate split, pinned by `CASPool.SkipAccessCheckStillEnforcesSingleAttemptGate`). The residue is observability: nothing tells the operator the probe was skipped, and the probe's own step-8 text claims the versioning check "has no override", which is false. Fix: log the skip at default level (with what is consequently unverified) and correct the message. P3. Behavior-only, no wire-format change.

- **[versioning-enabled-after-mount] Versioning enabled AFTER mount: misclassified error, delete-marker check at 1 of 8 sites (2031-triage CAS-029)** — {#versioning-enabled-after-mount} — A mandatory BEHAVIOURAL probe at every writable mount detects a versioned bucket — confirmed the mechanism still exists, now named `removeOrReportDeleteMarker` (`Backend/CasProbe.cpp:24,146,177`; the audit's original citation used the pre-rename name `created_delete_marker`) — and it rejects a versioned bucket on AWS and on any S3-compatible store regardless of the config check. Three narrow residuals stand, not independently re-verified line-for-line in this pass but not contradicted by anything found:

  - versioning turned ON **after** the mount surfaces as `LOGICAL_ERROR` for a state an operator can reach — reclassify (`CORRUPTED_DATA`-class or a named CAS error), per [[feedback_logical_error_tests_death_split]];
  - the delete-marker check is consulted at only ONE of the eight destructive delete sites, so the post-mount case is caught late and only on the blob-body path — decide whether the check belongs in the shared delete helper;
  - the GCS config check fails open, and `skip_access_check` skips the probe entirely (see {#skip-access-check-no-signal}). Update 2026-09-02: this is the decided behaviour, not a residual — an unverifiable versioning probe logs a warning and the mount proceeds, because the live stand's credential lacked `storage.buckets.get` and the refusal made a missing IAM grant a hard outage. A probe that verifies `Enabled` still refuses.

  Behavior-only, no wire-format change.

- **[control-object-read-precap-materialization] Control-object bytes are materialized whole before the format cap is checked (2031-triage CAS-036)** — {#control-object-read-precap-materialization} — Every control-object read is `Backend::get` → whole body into a `String` → `openObject`, which is where the per-format `object_cap` first fires (`Backend/CasObjectStorageBackend.cpp:359` `readStringUntilEOF`). `get` already HOLDS the authoritative size — it HEADs the key first and passes `hr->size` down — so nothing stops a pre-read gate except that `get` is format-agnostic and no caller passes its cap down; still true, no `getControlObject` wrapper exists. Consequence today is a transient allocation the size of whatever sits at the key before the cap can refuse it; under the memory tracker that surfaces as `MEMORY_LIMIT_EXCEEDED` on a GC/mount/recovery thread instead of the `CORRUPTED_DATA` the caps exist to produce. Fail-loud either way, and only a bucket-credential holder can plant such an object ([`pool-trust-boundary-undocumented`](docs-and-cleanup.md#pool-trust-boundary-undocumented) — that credential is the whole trust boundary), hence P3, not a security defect.

  Fix direction: give `get`/`getStream` an optional expected-cap argument (or a thin `getControlObject(FormatId, key)` wrapper) and refuse `hr->size > object_cap` before the read.

  Second, independent residue in the same read: `JsonObjectReader::nextKey` de-duplicates keys with a linear `std::find` over a `std::vector<String>` (`Formats/CasTextFormat.cpp:195-227`, confirmed still linear), so one line with k distinct keys costs Θ(k²) comparisons. The line caps bound k, but the `RefLog`/`RefSnapshot` line cap is 64 MiB — millions of keys, i.e. a single planted record that pins one thread for a long time. Cheap fix: a sorted/hashed seen-set, or a key-count cap per object. Both fixes are behavior-only, no wire-format change.

- **[manifest-digest-by-reencode] The manifest payload digest is a canonical re-encode, which makes the format's `Tolerant` key policy inert (2031-triage CAS-041)** — {#manifest-digest-by-reencode} — `decodePartManifest` verifies `payload_digest` by re-encoding the decoded model (`Formats/CasPartManifestFormat.cpp:300-301`, `computePayloadDigest` deep-copies the manifest and calls `encodePartManifest`); confirmed unchanged, format still `KeyStrictness::Tolerant` (`Formats/CasFormat.cpp:127`). Two residuals, neither a live bug:

  - **Design contradiction, not a reachable failure.** `cas_part_manifest` is registered `Tolerant` and the format framework explicitly plans for additive changes that keep the old reader floor — but a tolerated unknown key cannot survive a digest computed from what the local struct can re-emit, so for this one format the tolerance affordance can never be used. The consequence ("a manifest written by any other generation reads as `CORRUPTED_DATA`") is NOT reachable today: `currentCompatibilityVersion()` always stamps `G_BUILD` and there is no write-down-to-floor policy (tracked as B180), so a newer object is refused earlier and louder by `checkCompatibility`, and every generation bump so far is recreate-only.
  - **Cost, measured.** The recompute was 27-63% of total decode time in the original benchmark, plus two extra transient copies of the payload, worth bounding given the 256 MiB `object_cap` for this format.

  **Needs a format version and a compatibility path (format frozen since 26.6.4):** either fix option changes what the persisted `payload_digest` field means. Digesting the wire bytes directly (instead of the re-encoded canonical form) changes the verification semantics for every manifest ever written — it must be gated by generation so old manifests keep verifying against the re-encode while new ones use the wire digest. Dropping the format to `Strict` is a generation-bump decision with the same requirement. Settle as part of the format-freeze pass together with {#cas-format-version-floor} and {#codecs-and-protocol}.

- **[manifest-encoded-cap-checked-after-materialization] The manifest encoded-size cap is checked after the canonical text is materialized (2031-triage CAS-113)** — {#manifest-encoded-cap-checked-after-materialization} — MINOR (consistency; loud and fail-closed, unreachable under the caps that precede it). `stageManifest` encodes the whole canonical text and only then compares it against the cap (`Pool/CasPartWriteTxn.cpp:636-638`, `kMaxManifestEncodedBytes = 256 MiB`, confirmed unchanged). The ref lane answers the same question the other way round: `admits` decides whether one MORE row still fits *before* any encoding, off O(1) incremental body-byte counters; `Formats/CasByteBudget.h` states the rule explicitly, already used by `Formats/CasRefCatalogFormat.cpp` and `Formats/CasFoldSealFormat.cpp` — but not here. Not a release concern: the entry-count cap, the per-entry inline cap and the total inline cap are all checked before the body is built, so the 256 MiB text is unreachable for any realistic part folder. Owed: the same additive pre-encode reservation the other control objects use (an entry-count × worst-case-per-entry reservation plus the fixed frame, via `fitsObjectCap`). Behavior-only, no wire-format change.

- **[blob-envelope-never-read-back] The blob envelope's forensic fields still have no read-side consumer beyond one new caller (2031-triage CAS-089)** — {#blob-envelope-never-read-back} — Every blob body is `[fixed-length envelope][payload]`; the read path takes the payload offset from pool meta rather than from the object (`CasManifestReader::locate` returns `.offset = meta.blob_header_len`, consumed by `getBlobViewPlan`/`readBlobPayload`). `decodeEnvelopeHeader` used to have exactly one non-test caller (`SYSTEM CAS INSPECT`, `Tools/CasInspect.cpp:548`) — **this has changed**: `ContentAddressedTransaction.cpp:317-320` now calls it on the S3-native-staging retag/publish path (added by `907c3b5ce7d` "Publish CAS blobs after mandatory `HEAD`"), validating `decoded.header_len == header_len` before republishing a staged object as a blob. The design is otherwise unchanged and still deliberate (constant-shift locate, no per-object header read on the general path; divergence between an object's real envelope length and the pool's `blob_header_len` remains unreachable for the reasons already documented).

  Residual for the format-freeze pass: `decodeEnvelopeHeader`'s `object_size` parameter is still unused inside the function itself (`Formats/CasBlobEnvelopeFormat.cpp:235`, still `/*object_size*/`) even though callers now pass a real value — either give it a real consumer or drop it. The remaining open question is narrower than before: decide whether the envelope's `v`/`tag`/`bld` forensic fields need any further read-side use, and whether fsck's `detail` mode should sample-decode one to prove `header_len == blob_header_len` outside `INSPECT`/the staging retag path. No integrity item either way: a wrong offset hands MergeTree shifted bytes, which its own compressed-block checksums reject loudly.

- **[staged-inline-hardlink-no-dst-buildtxn] The staged-Inline arms of `createHardLink` / `moveFile` never establish the destination `PartWriteTxn` (2031-triage CAS-128)** — {#staged-inline-hardlink-no-dst-buildtxn} — `f7539af045c` ("inline-only part must create a Build") fixed exactly one of the three places that can push an `EntryPlacement::Inline` entry into a part staging: the inline WRITE callback. The two transfer paths were not fixed and, confirmed still not fixed:

  - `createHardLink`, staged-source arm — the `Blob` case calls `adoptStagedBlob(..., buildFor(*dst, dst_st), ...)` (`ContentAddressedTransaction.cpp:~1225`), the `Inline` case falls through to a bare `dst_st.entries.push_back(...)` with no `buildFor`.
  - `moveFile`, staged-entry arm — `buildFor(*dst, dst_st)` is still gated behind `entry.placement == Cas::EntryPlacement::Blob` (`ContentAddressedTransaction.cpp:~1561-1575`), so a CROSS-PART move of an Inline entry leaves the destination staging with entries and no build.

  `publishStaging` then throws `LOGICAL_ERROR` "staged entries or removal marks for {}/{} without a Build" — unless the destination ref happens to be already committed, in which case the repoint branch tolerates a null build. Fail-closed and loud; but under `abort_on_logical_error` it is a server abort. Not reachable from production today: every MergeTree `createHardLink` call site carries forward from a COMMITTED source part, and the part-file `moveFile` caller renames within ONE part directory, so `&src_st == &dst_st` and the build already exists from the inline write. Latent-shape hardening, not a live bug.

  Fix: add the idempotent `buildFor(*dst, dst_st)` to both Inline arms, and add gtest cases next to `CASWiringWrite.InlineOnlyPartPublishesWithoutBuildCrash` (`src/Disks/tests/gtest_ca_wiring.cpp:828`). Behavior-only, no wire-format change.

- **[sec4-decoder-size-bounds] decoders lack an explicit size bound for a valid-CRC oversized object (2031-triage, needs re-scoping)** — {#sec4-decoder-size-bounds} — DESIRABLE (security-relevant, SEC-4) — Originally framed around `decodeRootShard`/`decodePartManifest`-class decoders; `decodeRootShard` no longer exists (removed with `RunFile`/formats v3, see below). `decodePartManifest` (`Formats/CasPartManifestFormat.cpp:139`) still exists, under a 256 MiB `object_cap` (see {#control-object-read-precap-materialization}) plus a 1,048,576-entry write-side cap (`Pool/CasPartWriteTxn.cpp:55`). A pool-write-capable party could still place an enormous but validly-framed object; whether current GC shard/manifest decoders validate a size bound proportional to declared entry counts (not just the outer object cap) needs re-verification against today's class names before this item can be closed or re-scoped precisely. Same family as {#gc-shards-no-upper-bound}.

- **[mixed-ca-tiered-topology] `getStorageObjects` cannot express a blob's payload offset — move-out of a CA disk copies envelope bytes (2031-triage CAS-020)** — {#move-out-copies-envelope-bytes} — `StoredObject` (`Disks/DiskObjectStorage/ObjectStorages/StoredObject.h:16-29`) still has no offset field (`ContentAddressedMetadataStorage.cpp` `getStorageObjects`; the envelope header is ≥225 bytes, `CasManifestReader.cpp`), so any consumer that server-side-copies those keys copies the envelope, not the file. `clonePart` still branches on the DESTINATION only (`DataPartStorageOnDiskBase.cpp:771`, `dst_disk->isContentAddressed()`), so a MOVE **out** of a CA disk falls into `DiskObjectStorage::copyFile`, and `DataSourceDescription::operator==` (`DiskType.cpp:35`) still ignores `metadata_type` — a CA s3 disk and a plain s3 disk on the same endpoint compare EQUAL, so `copyFileImpl` takes the raw server-side copy. The same class reaches `BackupWriterS3/Azure/Disk::copyFileFromDisk` through `getBlobPath`. No move-out refusal exists.

  Loudness correction: every real part has inline files (≤1 MiB) whose storage key is `""`, so the operation aborts loudly — garbage objects plus a confusing error, not silent corruption. Hence P2, not a release blocker.

  The FETCH-side half of the mixed topology is designed and tested (a `[local] then [cas]` policy relinks onto CA and honours a `TTL ... TO DISK` rule afterwards: `test_tiered_policy_relinks_onto_cas_over_volume_order`, `test_relink_wins_over_ttl_then_mover_converges`, `tests/integration/test_cas_replicated_relink/test.py:992,1162`, both confirmed still present; spec `docs/superpowers/specs/2026-09-03-cas-fetch-forced-relink-design.md`). The move-OUT leg above is still open, and declaring the topology supported needs it fixed first.

  Fix options: (1) refuse move-out/copy-out on a CA source with a clear message (CA-local, preferred first step), or (2) make `DataSourceDescription` equality account for `metadata_type` — that is generic disk code, needs the upstream-consult step ([[feedback_upstream_code_consult_first]], [[feedback_cas_upstream_coupling_minimization]]) first. Behavior-only either way, no wire-format change.

## Ref ledger objects (`_log`, `_ckpt`, `_snap`, catalog) {#ref-ledger-objects}

- **[TXN-ONE-PIPELINE follow-up] committed-ref DDL overlay** — HARD — The TXN-ONE-PIPELINE initial landing implements the one-overlay invariant for the part-build write path only. Committed-ref DDL ops (DROP/MOVE/RENAME TABLE via `removeDirectory`/`removeRecursive`/`republishRef`/`dropNamespace`) and verbatim table/mountpoint files stay the immediate class (durable-at-call-time), not overlay-deferred. Follow-up = execute Appendix-A Tasks 1.2/1.3-DDL/1.4-DDL (a `pending_ref_ops` overlay `{Drop,Move,Replace}` keyed by `(ns,ref)`, materialized in `commit` after `publishStaging`, plus the new read surface so transaction reads answer "ref dropped/moved"); confirmed `pending_ref_ops` does not exist anywhere in either `cas-gc-rebuild` or `altinity/antalya-26.6`, so no part of this has landed. Deferred because it fixes no known motivating bug and has the highest regression risk (interacts with the empty-cover `commitTransaction` workaround and DROP/DETACH/ATTACH rollback); gate before doing it — audit that no single CA transaction interleaves an overlay-deferred part op with an immediate DDL/verbatim op order-sensitively. Interim risk: a DDL/ALTER that applies a durable ref-op then aborts before disk commit leaves the early-applied drop — narrow, not hit by the INSERT-sink abort, and covered by the DDL-exercising stateless/soak gates (a dangling/lost-part there = STOP + pull that op's overlay-deferral forward). (Orphaned-open cluster C-1118 describes this same overlay mechanism — already tracked, folded in as confirmation.)

- **[ref-table-64mib-admission-ceiling] The per-namespace 64 MiB ref-table budget is a hard per-table ref ceiling with no spill path (2031-triage CAS-111)** — {#ref-table-64mib-admission-ceiling} — Every state-growing ref op is previewed against two whole-table encodings and refused when either would pass 64 MiB: `admits` encodes the hypothetical complete snapshot and the hypothetical whole-namespace removal transaction (`Pool/CasRefProtocol.cpp:718-736`, confirmed unchanged), and the refusal is `LIMIT_EXCEEDED`. One namespace is one table, one committed row is one part folder, and a snapshot row is on the order of 75-95 bytes for realistic part names, i.e. a ceiling around 0.6-0.9 M refs per table.

  Failure class: fail-closed and loud, checked before any object is created, no corruption and no partial publication. But the refusal covers only GROWTH, and a merge grows before it shrinks, so a table at the ceiling cannot merge its way back down — only removals (`DROP PARTITION`, part removal, `DROP TABLE`) shrink the table. Reachability is well above MergeTree's own default active-part ceiling (`max_parts_in_total = 100000`), so getting there needs that setting raised several-fold plus outdated parts still holding refs — hence P2, not a release blocker.

  Owed: (a) a `CurrentMetrics`/`system.` surface for per-table budget consumption plus a WARNING well before the wall — confirmed no such surface exists in `Pool/CasRefLedger.cpp` today; (b) a design answer for tables that legitimately want more refs — a chunked/multi-object snapshot, or a partitioned ref table — since today the only way out is deleting parts. Same family as {#manifest-inline-budget-no-spill}. Behavior/observability-only, no wire-format change for (a); (b) may need a format version if it changes the snapshot's on-wire shape.

- **[freeze-name-reuse-merges-shadow-ref] FREEZE reuses a backup name silently on CA: `isDirectoryEmpty`'s part-dir short-circuit disables the `DIRECTORY_ALREADY_EXISTS` guard (2031-triage CAS-086)** — {#freeze-name-reuse-merges-shadow-ref} — P3, narrow but SILENT. `ContentAddressedMetadataStorage::isDirectoryEmpty` (`ContentAddressedMetadataStorage.cpp:1928-1945`, confirmed unchanged) deliberately answers `true` for any part-shaped directory, including a SHADOW part dir — the short-circuit exists so `DiskObjectStorage::removeDirectory` reaches the ref-unlink instead of throwing `CANNOT_RMDIR`, which is right for the removal path and test-pinned.

  The side effect is on the FREEZE path: `Backup` refuses a destination that exists and is not empty, which upstream is what makes a second `ALTER TABLE ... FREEZE WITH NAME 'x'` fail loudly for an already-frozen part. On CA the guard never fires, so the second freeze stages into the SAME shadow ref and `publishStaging` takes the existing-view repoint arm, merging the old frozen manifest's untouched entries with the new ones. Re-freezing an unchanged part is idempotent and harmless; re-freezing a DIFFERENT part that carries the same part name (after `REPLACE PARTITION` / `ATTACH PARTITION FROM`, which can reuse `all_1_1_0`) silently produces one frozen ref mixing files from two snapshots, where upstream would have refused the operation.

  Cross-disk `ATTACH PARTITION FROM` into a content-addressed disk now works after `cfe9a6a3615` (confirmed present, ancestor of HEAD), so the local→CAS route to this state is reachable instead of failing earlier in `freezeRemote`. Reconsider this item's priority against that wider reachability.

  Fix options, both small: teach `isDirectoryEmpty` to keep the listing-based answer for shadow part dirs (the removal-path rationale only covers live/detached part dirs), or reject a shadow ref that already exists on the FREEZE staging path. A gtest next to the existing shadow-shape cases plus a stateless `FREEZE WITH NAME` twice case would pin whichever is chosen. Behavior-only, no wire-format change.

- **[nonatomic-reserved-name-fold-no-refusal] A non-Atomic database or table literally named `detached`/`moving` is folded as the reserved dir with no refusal (2031-triage CAS-087)** — {#nonatomic-reserved-name-fold-no-refusal} — P3, accepted-limitation half already pinned, missing half is the fail-closed refusal. `findPartDirComponent` scans for a `detached`/`moving` component before the right-to-left part-dir grammar scan (`Parts/PartPathParser.cpp:205-221`, confirmed unchanged, `kDetachedDirName`/`kMovingDirName` only used in this ordering scan); the ordering is load-bearing. The consequence is a deliberately accepted limitation, documented and pinned by `CASPartPathParser.DetachedNamedTableIsKnownAmbiguityFoldedAsReservedDir`.

  What is NOT covered: nothing refuses such a table. Under a deprecated `Ordinary` database (default `false`) a table named `detached` gets folded parts, and with the DATABASE named `detached`, all tables in it collapse onto shared refs, fighting over promote conflicts. Failures there are loud, but the config is silently accepted rather than refused. Fix: refuse at table-attach/mount time a non-Atomic relative data path whose db or table component equals `kDetachedDirName`/`kMovingDirName`, naming the reserved name in the message. Same class as the DiskEncrypted-over-CA refusal item. Behavior-only, no wire-format change.

- **[checknamespace-admits-dot-segments] `Layout::checkNamespace` is the only CAS path validator that admits `.` and `..` segments (2031-triage CAS-091)** — {#checknamespace-admits-dot-segments} — `Layout::checkNamespace` (`Formats/CasLayout.cpp`, confirmed unchanged) rejects an empty namespace, an empty segment and the reserved `_files`/`_manifests` segments — but NOT a `.` or `..` segment. Every sibling validator in the tree does reject them: `validateServerRootId`, `isCanonicalRefName`, `isCleanRelativeNamespaceFileName`, the manifest entry-path check (whose comment even claims parity with `checkNamespace` — false at HEAD).

  The mechanism the divergence would enable is real, not theoretical: for `ObjectStorageType::Local` the backend is auto-selected into `EmulatedSingleProcess` and keys are joined under the disk root via `getCommonKeyPrefix`, i.e. they ARE filesystem paths, so a namespace segment `..` would escape the pool root. No production reachability today (every live namespace is built from escaped identifiers or a hex UUID; the one user-supplied string on the shadow path is the FREEZE backup name, and MergeTree escapes it before it becomes a directory).

  Fix is one line plus prose: add the `.`/`..` segment rejection to `checkNamespace`, which also makes the two "same hygiene" comments true. Worth a gtest case next to the existing namespace-validation cases. Behavior-only, no wire-format change.

## GC objects {#gc-objects}

- **[outcome-log-oc-not-required] `decodeOutcomeLog` does not require the outcome/kind fields** — {#outcome-log-oc-not-required} — MINOR — `decodeOutcomeLog` (`Formats/CasGcOutcomesFormat.cpp:67-119`, confirmed unchanged) sets `e.kind`/`e.outcome` only when the corresponding wire key is present, so a record without them decodes with the struct defaults (`OutcomeKind::Spared`, `ObjectKind::Blob`) instead of being refused. (Field names were renamed by the wire-keys semantic rename — `GcOutcomesWire::kind`/`::outcome`, no longer the original `k`/`oc` — the gap itself is identical.) Reachable only through the byte-adopt arm on a foreign/damaged log, and the sole consumer is the round report's tally — no deletion or liveness decision reads it — so the impact is a skewed counter, not a safety hole. Owed: the same required-field refusal the fold-seal codec already got ({#seal-decode-remaining-fields}). Behavior-only, no wire-format change.

- **[gc-state-encode-no-line-cap] `encodeGcState` does not enforce the line cap its own decoder enforces** — {#gc-state-encode-no-line-cap} — MINOR — `decodeGcState` reads the body with the 64 KiB `line_cap` while `encodeGcState` (`Formats/CasGcStateFormat.cpp:37-40`, confirmed unchanged) checks only `gc_shards >= 1`, so unlike `encodeFoldSeal` (which calls `checkLineBytes` per line) nothing stops the writer from persisting a `gc/state` its own reader would refuse. The only variable-length field is `msc`, an object key returned by a LIST page, bounded by the backend's key length (~1 KiB) — unreachable today and would fail closed (`CORRUPTED_DATA`, GC wedged until repaired) rather than corrupt anything. Owed: the symmetric encode-side cap check. Behavior-only, no wire-format change.

- **[gc-shards-no-upper-bound]** — MINOR — `gc_shards` is validated for `!= 0` at every boundary (`ContentAddressedSettings.cpp:62,231-236`, `Pool/CasPoolMeta.cpp:112-113`, decode sites — all confirmed unchanged) and never for an upper bound, while the value sizes per-round vectors in the GC hot path. A pool-write-capable party (or a fat-fingered creation-time setting) can therefore make every GC round die in allocation. Fails closed and loudly — no corruption, no out-of-range indexing, and the durable pair is cross-checked. Owed: a sane ceiling (a small constant, or one derived from the fold-seal reservation) at the setting boundary and in `decodePoolMeta`. Same family as {#sec4-decoder-size-bounds}. Behavior-only, no wire-format change.

- **[gc-shards-config-override-silent] adopting the pool's `gc_shards` over the node's configured value is silent** — {#gc-shards-config-override-silent} — MINOR (operability) — `Pool::open`/`openForDecommission` still overwrite the configured value with the durable one with no signal (`Pool/CasPool.cpp:538`, `:959`: `config.gc_shards = meta.gc_shards;`, confirmed no nearby `LOG_WARNING`), and `PoolMeta::createOrValidate` returns the existing meta without looking at the passed `gc_shards`. Pool-authority is the intended design and the setting is documented creation-time-only, but an operator who edits `<gc_shards>` on an existing pool gets no signal at all. Owed: one `WARNING` naming both values when they differ. Behavior-only, no wire-format change.

- **[numeric-parse-and-window-wrap] The `std::stoull` key-number parses accept `-1` and the manifest read window can wrap (2031-triage CAS-037)** — {#numeric-parse-and-window-wrap} — Three GC key-shape parses use `std::stoull` inside `catch (...)` (`Gc/CasGc.cpp:1487,1619,4291`, confirmed still present, shifted only by line count from the original 1488/1619/4094). The catch handles junk, but `std::stoull("-1")` does not throw — it returns `UINT64_MAX` — so a key named `.../gc/gen/-1/...` parses as a legitimate generation, which at the REBUILD site flows into `max_gen + 1`, wrapping to 0 and handing REBUILD a generation number the code's own comment forbids ("must never collide with debris of the lost era"). The same lesson was already learned and fixed elsewhere in this tree with `std::from_chars` (`ContentAddressedMetadataStorage.cpp:332-340`, commit `fc89b827d74`); these three sites did not get it. Fix: `std::from_chars` at all three, plus a saturating/checked successor for `max_gen + 1`.

  Related in the same class: `readBlobPayload` forms the read window as `location.offset + location.length` twice, where `length` is the manifest's `sz`, parsed with `readIntText`'s default `DO_NOT_CHECK_OVERFLOW`. A `sz` near `UINT64_MAX` wraps the sum below `offset`, and `ReadBufferFromFileView` has no bound precondition — the window collapses to an immediate EOF (loud failure downstream), so this half is robustness, not silent corruption. Fix on the CAS side (validate `sz` or use a saturating add) rather than in the generic upstream buffer. Behavior-only, no wire-format change.

- **[s3-staging-reclaim-only-at-mount-start] S3 staging debris is reclaimed only at mount start and is invisible to fsck (2031-triage CAS-081)** — {#s3-staging-reclaim-only-at-mount-start} — An aborted/exception-unwound transaction deliberately leaves its S3 staging objects in place, because a staging object is a re-readable publication source and must outlive one failed attempt; shared monotonic `publication_attempted` state ensures only the first absent publication may use verbatim native copy. That part of the design is settled. What is NOT covered is the reclaim side:

  - `sweepOwnMountStaging` (`Pool/CasServerRoot.cpp:1804`) still has exactly ONE call site, at mount start (`ContentAddressedMetadataStorage.cpp:893`, confirmed unchanged), gated on `staging_backend=s3` + `!read_only`. There is no periodic in-mount reclaim, so under an opt-in `staging_backend=s3` disk the staged bytes of every killed/cancelled INSERT, failed mutation and aborted MOVE accumulate for the WHOLE uptime of the mount and are reclaimed only by the next restart.
  - GC never lists `staging/` (a top-level prefix disjoint from `blobs/`), and `runFsck` inherits the same blob-discovery prefix, so the debris does not appear as `unaccounted`. (For a DEAD member the drain does exist: `SYSTEM CAS DROP POOL MEMBER` removes `staging/<victim_srid>/` and reports `staging_objects_removed`.)

  Fix direction: run the same prefix sweep periodically (e.g. from the GC scheduler's own pacing loop, still fenced to THIS mount's `staging/<server_root_id>/` prefix) with an age filter that cannot reach an in-flight staging object, and surface the staging-object count/bytes in an introspection surface. Low urgency: the whole path is opt-in and OFF by default, and every restart clears the residue. Behavior-only, no wire-format change.

- **[emu-token-state-clock-skew-leak] Emulated token-state expiry compares an fs-mtime etag against the local clock (2031-triage CAS-067)** — {#emu-token-state-clock-skew-leak} — MINOR (emulated mode only — CI, unit tests, local development; no S3/GCS pool is affected). `emuMintToken` seeds its token from the object's etag, which `LocalObjectStorage` derives from the file's mtime in nanoseconds. The bound on `emu_token_state` expires an entry only when that etag is "comfortably in the past" relative to the process's own `system_clock`: `etagComfortablyInThePast` (`Backend/CasObjectStorageBackend.cpp:391`, confirmed still etag-vs-`now_ns`, used at deletion `:462`, `:999`). Those two clocks are the same clock on a local filesystem, but not necessarily on a shared mount, and not across an NTP step — a leaked entry only makes a later same-key recreate mint a disambiguated `etag#N` token (still unique, still fail-closed), so no correctness impact, just ~100 B per distinct deleted key leaked in a long-running emulated-mode process under skew.

  Fix direction: derive the expiry decision from a monotonic, locally-generated stamp (the `queued_at_ns` already recorded) instead of re-reading the storage-supplied etag; or cap `emu_token_state` by size as a backstop. Existing unit coverage (`gtest_cas_backend.cpp:847-919`) already has the injectable clock/etag doubles needed for a failing-first test. Behavior-only, no wire-format change.

- **[ca-scratch-path-docker-entrypoint-permission] a CA disk's default scratch path can be root-locked by the docker entrypoint** — {#ca-scratch-path-docker-entrypoint} — DOC — If a sibling `local`-type disk declares an explicit `<path>` under the same `<data-path>/disks/` tree as a CA disk's default (undeclared) scratch path, the official docker image's entrypoint `chown`s only the leaf it was told about, leaving the shared `disks/` parent root-owned — the CA disk's later scratch-dir creation then throws `Permission denied` and the server exits before listening.
