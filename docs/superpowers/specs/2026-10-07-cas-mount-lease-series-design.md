# CAS mount lease: серия малых PR {#cas-mount-lease-series}

Ревизия 8, 2026-10-09. Статус: PR 1–5 и 7–16 реализованы; PR 6 отозван; 17a не начат; 17b и 18
отложены. Ревизия вносит решения владельца и факты реализации. Деление остановки на два класса —
**предварительное** (раздел «Остановка сервера»). История ревизий — в конце.

Сбой хранилища на 8 с стоит CAS-монтированию около 40 с без записи
([#2431](https://github.com/Altinity/ClickHouse/issues/2431)): фоновое продление lease сдаётся через
4 с, само фенсит монтирование и запускает remount под новым `writer_epoch`. Эта спека описывает,
как сделать продление и потерю lease простыми и предсказуемыми, что при этом видит оператор, и
делит работу на малые самостоятельные PR в `antalya-26.6-20261008` (ветка заморозки
`antalya-26.6`).

Три решения:

1. **Сбой хранилища — пауза, а не потеря.** Продление повторяется, пока хранилище не даст
   определённый ответ о слоте. Операции, которым нужен lease, отклоняются, пока подтверждённого
   lease не хватает; после подтверждения они продолжаются под тем же `writer_epoch`.
2. **Сервер останавливается, когда слот ему больше не принадлежит или машина lease не может
   безопасно продолжать.** Слот занял другой сервер, удалили или переписали — продолжать значило бы
   писать в чужой пул; сервер завершается штатно. Нарушен инвариант самого процесса — процесс
   завершается сразу, без shutdown. Если GC зафенсил наше собственное тело, та же нить закрывает
   старый epoch и берёт слот заново под новым.
3. **Настройки с именами, которые говорят, что произойдёт,** и пороги, напечатанные из того же
   расчёта, который применяет код. Ни одно значение по умолчанию не выводится из другой настройки,
   ни одна заданная настройка не игнорируется; lease, период и запас существующих конфигураций
   сохраняют смысл. Что меняется для той же конфигурации: реакция на потерю слота (остановка вместо
   remount, PR 12) и ожидание наблюдателей — не меньше lease, который объявляет держатель (PR 2).

Чего серия **не** делает: не меняет формат объектов; не сокращает ни одно ожидание наблюдателя; не
уменьшает резерв допуска до отдельного аудита поздней записи; не меняет значения по умолчанию.

## 1. Для оператора {#for-the-operator}

### Как это работает {#how-it-works}

Каждый сервер, который пишет в пул, держит в хранилище объект `gc/server-roots/<id>/mount`
и переписывает его условным `PUT` раз в период продления (по умолчанию 10 с). Пока объект
обновляется, остальные участники пула считают сервер живым.

Если хранилище не отвечает:

- сервер продолжает попытки продления примерно раз в секунду, сколько бы это ни длилось;
- операции продолжаются, пока подтверждённого lease хватает на их завершение;
- потом они **ставятся на паузу**: запрос получает ошибку с объяснением и повторяется клиентом
  как обычная сетевая ошибка. На паузу встают условные записи, затем удаления, публикации и
  чтения манифестов, которых нет в кеше (им тоже нужен lease — чтение на монтировании без lease
  отклоняется);
- когда хранилище отвечает и продление подтверждено, операции продолжаются. Ничего не
  перемонтируется, `writer_epoch` прежний, таблицы не перечитываются.

Если слот отобрали — другой сервер с тем же `server_root_id` получил его, слот удалён или в нём
данные, которых этот сервер не писал, — **сервер останавливается штатно** с одной строкой `ERROR`, в
которой сказано, что найдено в слоте. Удалённым слот считается, только когда `GET` ответил `404` и
`LIST` префикса ключа его тоже не показал. Остальные диски этого сервера останавливаются вместе с
ним. При настроенном автоматическом перезапуске супервизор запустит сервер снова; при живом
конкуренте старт не проходит, и перезапуски повторяются, пока оператор не уберёт дубликат.

Если нарушен инвариант самого процесса — в нашем идентификаторе ref-журнала лежит объект, которого
этот процесс не писал, или сломалась машина продления, — процесс **завершается сразу** строкой
`FATAL`, без shutdown: shutdown писал бы farewell и checkpoint под идентичностью, которую мог взять
другой процесс.

Если наше тело в слоте зафенсил GC (любого участника пула: `computeHeartbeatFloor` перебирает и
свой слот; этот сервер не продлевал lease дольше окна наблюдения), сервер закрывает старый
`writer_epoch`, дожидается завершения его recovery и публикаций и берёт слот заново под новым epoch.
Операции старого epoch отклоняются и повторяются клиентом. Окна наблюдения здесь нет, верхняя
граница времени не обещается.

### Состояния {#states}

Состояние монтирования вычисляется из двух фактов: подтверждённый дедлайн текущего epoch и
необратимая причина завершения, если она есть. Локальные колонки `system.cas_mounts` читаются без
обращения к хранилищу (раздел «Системная таблица»), даже если нить продления застряла в запросе.
Таблица ниже — словарь с PR 9a. Между PR 8 и PR 9a словарь сегодняшний: истёкший lease виден как
`not_live` с причиной `lease_expired`.

| `lifecycle` | `lifecycle_reason` | Что это значит | Условные записи | Удаления, публикации, некешированные чтения |
|---|---|---|---|---|
| `live` | — | lease подтверждён, его хватает на запись | идут | идут |
| `paused` | `renewal_overdue` | продление не подтверждено так долго, что остатка lease не хватает на условную запись; продление повторяется | отклоняются | идут до своего порога |
| `paused` | `lease_expired` | lease кончился; продление повторяется | отклоняются | отклоняются |
| `paused` | `fenced_by_gc` | GC зафенсил наш epoch; идёт закрытие старого epoch и получение слота под новым | отклоняются | отклоняются |
| `paused` | `remounting` | только между PR 9a и PR 14: идёт существующий remount | отклоняются | отклоняются |
| `stopping` | `slot_taken`, `slot_absent`, `slot_corrupt`, `pool_identity_lost` | слот или пул больше не наши; запрошена штатная остановка сервера | отклоняются как повторяемые | отклоняются |
| `stopping` | `ledger_fault`, `local_defect` | нарушен инвариант процесса; процесс завершается без shutdown | отклоняются | отклоняются |
| `closed` | `forgotten` | оператор выполнил `SYSTEM CAS FORGET`; монтирование закрыто до рестарта | отклоняются | отклоняются |

`renewal_overdue` и `lease_expired` не хранятся: они следуют из дедлайна и часов. Хранятся
необратимое завершение, идущее получение заново и их причина. Отображение сегодняшних значений
(PR 9a; колонки становятся `Nullable` — смена типа, называется в разделе о смешанных версиях и в
`docs/en/antalya/cas/`): `not_live` → `paused`; `vanished`/`forgotten` → `closed`/`forgotten`;
`identity_lost` и `vanished`/`replaced` — до PR 14 без изменений, после — `stopping`/
`pool_identity_lost`; `constructing` и `shutdown` сохраняются. Каждый переход пишется в лог одной
строкой; если нить была занята запросом, строка пишется при обнаружении и называет, сколько
времени назад порог был пересечён. Повторные попытки продления не логируются.

Колонка `state` (`live`/`expired`/`fenced`/`terminated`/`corrupt`) описывает тело слота по wall-clock штампам
и часам этого сервера; решение «можно ли работать» даёт только `lifecycle`. На строках чужих
монтирований `lifecycle` и `lifecycle_reason` — `NULL`.

### Шкала времени {#timeline}

Настройки по умолчанию: lease 30 с, период 10 с, срок запроса 5 с, конверт запроса 7 с (раздел 4),
запас 2 с. Последнее подтверждённое продление началось в 0 с; с 10 с хранилище не отвечает.
Пороги — из того же расчёта, что применяет допуск (`CasRequestBudget`); допуск отказывает, когда
остаток **не больше** резерва. Все моменты отсчитываются от начала последнего подтверждённого
продления. Если PR 18 когда-нибудь войдёт, конверт станет равен сроку запроса, и пороги сдвинутся
(14 → 18 с, 21 → 23 с).

| Время | Что происходит | Состояние |
|---|---|---|
| 0 с | продление подтверждено | `live` |
| 10 с | пора продлевать; запросы падают; повторы раз в секунду | `live`, в таблице виден последний отказ |
| 14 с | остаток lease не больше резерва условной записи (`2 × 7 + 2`) | `paused`, `renewal_overdue` |
| 21 с | остаток не больше резерва операции с одним запросом (`7 + 2`): останавливаются `remove`, `removeManyWriteOnce`, `publish`, некешированные чтения манифестов | `paused`, `renewal_overdue` (та же причина) |
| 30 с | lease кончился | `paused`, `lease_expired` |
| не раньше 41,5 с после первого чтения токена GC | GC, который видит хранилище, вправе поставить `gc_fenced`: окно 31,5 с + его шаг 10 с. Фенс ставит следующий подходящий раунд GC (`cas_gc_interval_sec`, по умолчанию 60 с), обычно позже | `paused`, `fenced_by_gc`; после ответа хранилища — новый epoch |
| хранилище ответило | продление подтверждено; `live`, если остатка от `start + lease` хватает на запись, иначе `paused` и следующее продление сразу | `live` или `paused` |

Другой сервер с тем же `server_root_id` вправе забрать слот, когда видел токен неизменным
`L + L/20` плюс свой шаг опроса по своим часам, где `L` — больший из своего lease и lease,
объявленного в теле (раздел 3).

Продление, у которого потерялся ответ, тратит два запроса и может закончиться после 14 с; тогда
условные записи встают на несколько секунд при исправном хранилище — строка монтирования об этом
говорит.

Строка при монтировании, числа из кода:

```
CAS disk 'cas1' (server_root_id=…): renewal starts every 10 s. Without a confirmed renewal
conditional changes pause after 14 s; deletes, publishes and uncached reads after 21 s; the
lease ends after 30 s. Operations resume under the same writer_epoch after a confirmed renewal
that leaves enough lease. A renewal that takes the full request envelope of 7 s ends at 17 s,
after conditional changes pause. Another server may take this slot after it has seen the token
unchanged for 31.5 s plus its own poll step (cas_mount_lease_ms=30000,
cas_mount_renew_period_ms=10000, request envelope 7 s, cas_lease_safety_margin_ms=2000).
```

Строка печатается PR 9b. В ней `uncached reads` — некешированные чтения манифестов: чтение payload
(`readBlobPayload`) идёт мимо плоскости монтирования и lease не требует. Окно другого сервера в
строке посчитано по своему lease; lease, объявленный в теле (PR 2), строка не учитывает. Обе
формулировки — в списке отложенного.

Текст отказа при паузе:

```
CAS disk 'cas1': this change is not admitted: 14 s of the confirmed lease remain and a
conditional change needs more than 16 s (two requests of 7 s plus 2 s). Renewal keeps retrying;
changes resume after a confirmation that leaves enough lease. Last renewal error: PUT
gc/server-roots/…/mount: HTTP 503 Slow Down.
```

Если последняя ошибка — отказ класса `Refused` (`AccessDenied`, `MalformedXML`, …), последнее
предложение другое: `the object store refuses the renewal request (AccessDenied); changes resume
after the cause is fixed and a renewal is confirmed`.

Строка при остановке сервера:

```
CAS disk 'cas1' (server_root_id=…): the mount slot holds a body of another incarnation
(hostname=…, pid=…, server_uuid=…, writer_epoch=…, gc_fenced=…). New changes are closed;
server stop requested. Every CAS disk of this server stops with it. Check for two servers
sharing one server_root_id or two starts with one UUID.
```

Для `ledger_fault` и `local_defect` то же описание пишется на уровне `FATAL` и говорит, что процесс
завершается без shutdown. Восстановление после остановки текст называет так: добавить сервер заново
под новым `cas_server_root_id`. Восстановить прежний на месте сегодня нельзя: `SYSTEM CAS DROP POOL
MEMBER` не удаляет owner-anchor, а декомиссия поверх существующих данных отказывает.

Для отсутствующего слота строка сообщает доказанный факт («the mount slot is absent») и
отдельно, чем слоты удаляются («a slot is deleted by SYSTEM CAS DROP POOL MEMBER or by hand»);
для нечитаемого — что тело не декодируется; для продвинутого счётчика — «the writer epoch counter
of this server_root_id was advanced by another process (a second start or a decommission)».
Сведений о владельце такие строки не обещают.

### Настройки {#settings}

| Настройка | По умолчанию | Что значит | Область |
|---|---|---|---|
| `cas_mount_lease_ms` | 30000 | сколько этот сервер может писать после начала последнего подтверждённого продления; каждый наблюдатель ждёт не меньше этого, прежде чем фенсить или забрать слот. Операции останавливаются раньше — пороги печатаются при монтировании | только этот сервер; значение уходит в тело слота, наблюдатели его читают (PR 2) |
| `cas_mount_renew_period_ms` | 10000 | как часто начинается продление; тот же период — шаг, с которым этот сервер наблюдает чужие слоты | только этот сервер |
| `cas_attempt_timeout_ms` (имя `cas_request_deadline_ms` — с 17b, отложен) | 5000 | сегодня: таймаут одной операции сокета в попытке служебного запроса; конверт попытки — `таймаут + 2 × лимит соединения` (раздел 4). После 17b — срок сетевой части попытки: соединение, отправка, ответ, редиректы; DNS и учётные данные им не прерываются. Отправленный `PUT` мог примениться после обрыва ожидания | только этот сервер |
| `cas_lease_safety_margin_ms` | 2000 | запас в резерве каждого допуска, не «только при старте» | только этот сервер |

Ни одно значение не выводится из другого, ни одна заданная настройка не игнорируется: период по
умолчанию 10 с при любом lease, как сегодня; запас учитывается в резерве и после PR 18.

Расчёт один для допуска, строки монтирования, системной таблицы и текстов ошибок
(`CasRequestBudget`): резерв условной записи — `2 × конверт + запас`; резерв операции с одним
запросом — `конверт + запас`; конверт — сегодняшний `срок + 2 × лимит соединения` (раздел 4), после
PR 18 — `cas_request_deadline_ms`.

Проверка конфигурации — одно правило, как сегодня (`validateCasRequestBudget`), словами и с
числами: продление должно начинаться, пока условная запись ещё допускается — `период + резерв <
lease`. Что продление, занявшее весь конверт, кончается после порога паузы, сообщает строка
монтирования (предупреждение при значениях по умолчанию, которое нечем снять, не печатается).
Суммы считаются без переполнения; верхней границы lease нет.

Старые имена (PR 9b; 17b отложен):

| Старое имя | Что с ним |
|---|---|
| `cas_mount_lease_ttl_ms` | синоним `cas_mount_lease_ms` (PR 9b) |
| `cas_attempt_timeout_ms` | станет синонимом `cas_request_deadline_ms`, если 17b войдёт. Смысл числа поменяется: было ограничение одной операции сокета, станет — сетевой части всей попытки. Тот же `5000` отменит больше запросов; при монтировании печатаются оба смысла |

Задать новое имя и его синоним разными написаниями с разными значениями — ошибка конфигурации с
обоими именами в тексте; повтор одного ключа отвергает уже `loadFromConfig`. Написания без префикса
`cas_` остаются в том же статусе, что сегодня.

`cas_unsafe_remount_no_delay` остаётся: это настройка **старта** (`Pool::mountWritable`): после
`kill -9` не ждать окно наблюдения. К получению слота заново после фенса она отношения не имеет.

Разный lease на разных серверах пула безопасен (PR 2). Наблюдатель ждёт
`max(свой lease, объявленный) + 5 % + свой шаг`. Объявленный lease —
`expires_at_ms − started_at_ms`, если разность положительна, иначе 0: нет штампов, farewell (равные
штампы) или неверные даты — тогда наблюдатель ждёт по своему lease, как сегодня. Короче
сегодняшнего ожидание не бывает, новых путей фенса нет, поэтому версии разворачиваются в любом
порядке. Оговорка: пока в пуле есть наблюдатель без PR 2, он ждёт только свой lease; держатель с
более длинным lease может быть зафенсен им внутри своего права. GC пишет одну строку `WARNING` на
слот, если объявленный lease отличается от своего: узлы ждут объявленный lease, и более длинное
значение задерживает восстановление после падения этого узла.

### Системная таблица {#system-table}

`StorageSystemContentAddressedMounts::read` сегодня синхронно вызывает `listMounts` и только потом
отдаёт строки: при лежащем хранилище запрос висит. PR 9a даёт канонический локальный путь без I/O:
колонка `is_local`; блок кандидатов — две колонки, `disk` и `is_local`, по две строки на диск
(`is_local = 1` и заглушка `is_local = 0`); к нему до любого I/O применяется предикат запроса по
этим колонкам (предикаты по другим колонкам не применяются, как в `VirtualColumnUtils`); листинг
вызывается только для дисков, чья заглушка осталась. Обещанная форма — `WHERE is_local = 1`. Чужие строки читаются
одной попыткой (`Retry::once`); если листинг не удался, выдаётся одна строка с ошибкой листинга.
Без 17b одна попытка не ограничена по времени (раздел 4).

Проверяется SQL-запросом целиком со счётчиком вызовов бэкенда и зависшим чтением чужого слота.

## 2. Правила держателя {#holder-rules}

Одна нить на монтирование. Она продлевает lease и обрабатывает исход каждого продления.
Второй нити, парковки, поколений запросов на remount и окна наблюдения в runtime нет.

### Продление {#renewal}

- R1. Продление — одна логическая операция: `(ключ, тело, ожидаемый ETag, write_attempt_id, start)`
  фиксируются до первого запроса. Все физические повторы используют тот же кортеж. Новая
  операция не начинается, пока предыдущая не завершилась определённым исходом.
- R2. Продление идёт на плоскости `lease_requests` — это сегодняшняя `farewell_requests` (`Fence::open`,
  без lease-гейта), переименованная; сон между попытками обычный (R4); третьей плоскости нет. Нить вызывает движок с новой политикой «до определённого
  исхода, без дедлайна» (`Retry::bind` сегодня всегда даёт `now + окно`; политика добавляется в
  PR 8) и с темпом R4 вместо `Retry::backoff`: движок сам повторяет попытки, держит неясность
  внутри вызова и сверяет байты при разрешении.
  Определённый исход — ответ на вопрос «цел ли наш слот»: подтверждение своих байт (R3) или одно
  из наблюдений таблицы потерь. Не определённые исходы: таймаут, `5xx`, обрыв соединения —
  движок повторяет; `Refused` (всё из `isDefinitelyRefusedWrite`: `AccessDenied`, просроченный
  токен, `MalformedXML`, `EntityTooLarge`, …) — нить делает новый вызов движка с тем же кортежем,
  что допустимо потому, что `writeLoop` возвращает `Refused` только когда в вызове не было неясной
  попытки (тест «чистый `412` + отказ чтения», свойство модели); после `Refused` класса учётных
  данных (признак класса — типизированное поле `Refused`, которое `writeLoop` заполняет сам, не
  разбор текста) следующий вызов — через период продления, не через секунду: каждый такой вызов
  может сделать один успешный refresh и одну дополнительную попытку; `Conflict{NotObserved}` (чистый `412`, а чтение не удалось) —
  повторяется только чтение: `412` уже доказал, что precondition ушёл. Классификатор тотален: для
  каждого наблюдения и состояния памяти ровно одна строка — чтение, вернувшее наше последнее
  подтверждённое тело с ETag, равным precondition (несогласованное чтение), → новый вызов тем же
  кортежем; чистый `412`, а прочитаны точные байты текущей операции, → `slot_taken` (клон);
  в `Reacquire` поля равны GC-преобразованию, а ETag не равен сертификату, → `slot_corrupt`. `GaveUp` для этой политики возможен только по stop (`FenceLost` через `Liveness` в
  `gate`), не по дедлайну и не по исчерпанию.
- R3. Неясный исход `PUT` (ответ потерян) разрешается чтением и признаётся успехом только по
  точным байтам нашей операции, не по совпадению `write_attempt_id`, `uuid` или `epoch`.
- R4. Между попытками равномерно случайные 800–1200 мс от начала предыдущей попытки; чтение после
  неясного `PUT` не откладывается. Сон между попытками не длиннее 1,2 с и не требует пробуждения по
  stop: задержку shutdown ограничивает запрос в полёте, который без 17b не прерывается.
- R5. Успех устанавливает дедлайн `start + lease`, где `start` — начало логической операции по
  `CLOCK_BOOTTIME`. Ответ, чтение и повторы `start` не двигают. Если `start + lease` уже в прошлом
  или остатка не хватает на запись, запись остаётся на паузе, а следующее продление начинается
  сразу. Дедлайн публикуется под тем же мьютексом, под которым проверяется, что продление
  относится к текущему epoch: результат старого epoch не трогает дедлайн нового.
- R6. Пауза и истёкший lease продление не останавливают: плоскость `lease_requests` lease-бюджетом
  не гейтится. Останавливают только stop, shutdown и причины завершения.
- R7. Пауза не меняет `writer_epoch`, не отменяет допущенные операции и не трогает ref-таблицы.
  Допуск операции и проверка её завершения остаются обязательными; текущая ошибка и число
  физических попыток публикуются во время операции, не после неё.

### Потеря {#loss}

Решение принимается по **наблюдению**, не по коду исключения. Наблюдение — одно из трёх:
`Object` (прочитанные байты и их ETag), `ProvenAbsent` (авторитетное отсутствие, раздел 4),
`NotObserved`. Нить хранит два собственных тела (`MountLease`): последнее подтверждённое и текущее
неясное продление, если оно есть. Активный epoch — тот, под которым нить продлевает; выделенный
при получении заново — отдельное значение. Один классификатор наблюдения обслуживает продление и
получение заново; старт использует те же факты с другими полномочиями.

Колонка «Класс» — реакция по разделу «Остановка сервера»: **штатно** — `SIGTERM` своему процессу;
**сразу** — `LOG_FATAL` и `std::terminate()`.

| R | Наблюдение | Действие | Класс |
|---|---|---|---|
| R8 | `Object`: наше `(uuid, активный epoch)`, `gc_fenced`, и декодированное тело совпадает с одним из двух наших тел во всех полях, кроме `gc_fenced` и `seq` (`seq` увеличен так, как делает `computeHeartbeatFloor`); ETag запомнен как сертификат | закрыть старый epoch и получить слот заново; `paused` / `fenced_by_gc` | — |
| R9 | `Object`: наше `(uuid, epoch)`, тело не наше и не GC-преобразование наших (с `gc_fenced` или без) | остановка, `slot_corrupt` | штатно |
| R10 | `Object`: тело не декодируется | остановка, `slot_corrupt` | штатно |
| R11 | `Object`: наш `uuid`, другой epoch — больше активного (наш перезапущенный двойник уже забрал слот) или меньше (невозможное состояние); с `gc_fenced`, farewell-маркером или без | остановка, `slot_taken` | штатно |
| R12 | `Object`: чужой `uuid` — прочитанный прямо или чтением после проигранного условного `PUT`; наши байты под токеном, которого мы не писали; результат без тела — `NotObserved`, не наблюдение | остановка, `slot_taken` | штатно |
| R13 | `ProvenAbsent`: `GET` ответил `404`, и `LIST` префикса ключа не показал ключ (раздел 4) | остановка после подтверждения `LIST`, `slot_absent` | штатно |
| R14 | ошибка ref-полосы — `ledger_fault`: в идентификаторе ref-журнала, который принадлежит нам, лежит что угодно, кроме наших точных байт (чужая транзакция, `EpochSeal` преемника, недекодируемый объект); полоса в невозможном состоянии (например, не в `Ready` при выделении нового ID); recovery находит записи преемника под нашим живым epoch (отдельный PR вслед за PR 10); каталог ref-таблиц не декодируется или неоднозначен | остановка, `ledger_fault` | сразу |
| R15 | объединена с R14 | — | — |
| R16 | identity probe: `IdentityLost`, `Replaced`; `claimOwnerOrThrow`: owner tombstoned или чужой; owner-anchor, счётчик epoch, каталог или метаданные пула отсутствуют (после подтверждения `LIST`); корень данных принадлежит другому пулу | остановка, `pool_identity_lost` | штатно |
| R17 | дефект нашего кода: исключение, вышедшее из машины нити продления или получения заново (кроме `MEMORY_LIMIT_EXCEEDED`, раздел ниже) и не отнесённое к строкам выше по месту возникновения | остановка, `local_defect`. Нить не перезапускается | сразу |
| R18 | `SYSTEM CAS FORGET` | `closed` / `forgotten`; сервер работает | — |

Таблица действует только для writable-монтирования собственного `server_root_id` этого сервера с
фоновыми нитями. Монтирование инструментов без фоновых нитей закрывает диск вместо остановки
процесса. Пул декомиссии (`Pool::openForDecommission` выдаёт себя за жертву и продлевает её lease в
фоне) при любой строке R8–R17 закрывает запись и завершает команду `SYSTEM CAS DROP POOL MEMBER`
ошибкой `ABORTED` с той же причиной; получение заново и остановка процесса для него не действуют.
Удаления staging и mountpoint-объектов жертвы идут на отдельном движке без фенса
(`CasDecommission.cpp`); он получает `admit(liveness)` с предикатом латча admin-пула через
`weak_ptr` (операция живёт дольше `Pool`), и между шагами команда проверяет латч. Чего это не
покрывает: `sweepNamespace` идёт через `Pool::openRequests` (плоскость `gc_requests`), латч
admin-пула его не прерывает, а ошибки удаления там становятся предупреждениями. Удаление манифестов
по-прежнему защищает `manifestDeletionPremise`; повреждения данных через этот путь не показано.

Исключение по лимиту памяти не считается ошибкой нити: вся итерация продления и получения заново
идёт под `LockMemoryExceptionInThread(VariableContext::Global)` (глобальный tracker,
`max_server_memory_usage`), условный `PUT` выполняется на вызывающей нити с буфером по размеру тела.
Путь коммита ref-полосы (append, чтение и декодирование occupant) идёт под тем же guard, поэтому
лимит памяти там не ошибка полосы и отдельной ветки «повторить позже» нет. `std::bad_alloc`
остаётся R17.

Латч ошибки ref-полосы (R14): одна причина без типа и одна функция отчёта
(`reportLatchedFault`). Наблюдавшая нить ставит латч первым действием во **всех** вызывающих
ветках — `commitRefChunk`, разрешение wedge, `runRecoveryWalkOnce`, ворота свергнутой полосы в
`flushRefBatch` — до `fmt::format` и копирования ключей. Сырые факты (ключ, декодированный заголовок
или «не декодируется», текст исключения) идут только в сообщение. Recovery преемника по-прежнему
отличает записи предшественника от чужих: это нужно, чтобы поставить печать.

Решение о завершении необратимо для процесса; решение о фенсе необратимо для старого epoch.
Латч ставится **до** любого действия (лога, события, ожидания) той нитью, которая наблюдала;
поздний успешный ответ продления старого epoch или шага получения заново латч не снимает. Нить
продления читает латч под `driver_mutex` в одном шаге с открытием записи.

Ограничение формата, которое вводит R8: поле в `MountLease` добавляется только после того, как все
GC-узлы пула умеют его сохранять при фенсе; иначе фенс старым GC даст R9 и ложную остановку.

Что не ловится: клон виртуальной машины, байт-идентичный нашему процессу, пишет тела, которые
проходят R3 и R8. Это записано в документацию.

### Остановка сервера {#server-stop}

**Предварительно.** Деление на два класса — решение владельца от 2026-10-08, оставленное с
условием: shutdown над мёртвым CAS-диском не зависает. С латчем потери farewell и закрытие таблиц
отказывают за O(1): без ожидания lease и без серии запросов «до определённого исхода». PR 12
проверяет это тестами `CASRefLaneFault.ShutdownAfterATakenSlotSendsNothing`,
`…AnAbsentSlotSendsNothing`, `…AFaultSendsNothing` (запросов ноль) и процессным тестом с watchdog.
Если условие перестанет выполняться, штатный путь для внешнего класса пересматривается.

| Класс | Причины | Реакция |
|---|---|---|
| внешнее событие, инварианты процесса целы | `slot_taken`, `slot_absent` (после подтверждения `LIST`), `slot_corrupt`, `pool_identity_lost` | латч, запрос штатной остановки, строка `ERROR`. Farewell не пишется; таблицы закрываются; остальные CAS-диски останавливаются вместе с сервером |
| нарушен инвариант процесса | `ledger_fault`, `local_defect` | латч, строка `LOG_FATAL`, `std::terminate()`; shutdown не запускается |

Почему второй класс без shutdown: shutdown сам пишет — farewell в слот, закрытие `_ckpt` — под
идентичностью, которую, возможно, уже держит другой процесс. В базовом коде так же поступают с
нарушенным инвариантом `MergeTreeData.cpp` и Keeper (`LOG_FATAL` и `std::terminate()`), а штатную
остановку `BaseDaemon::terminate` просит сигналом `SIGTERM`.

Механизм: два процессных колбэка в `CA/` (`requestGracefulProcessStop`, `terminateProcess`), так что
`CA/` не зависит от `src/Daemon`; тесты их подменяют. Штатный колбэк по умолчанию —
`kill(getpid(), SIGTERM)`: сигнал процессу, не нити. `raise(SIGTERM)` (это `pthread_kill(self)`) не
работает: нити Poco блокируют `SIGTERM`, и сигнал, адресованный нити продления, остаётся висеть.
Сигнал процессу доставляется нити, которая его не блокирует; завершение ведёт главная нить через
`SignalListener`. Если `kill` не удался — `std::terminate()`: остановка, которую нельзя запросить, не
должна оставлять живой split-brain. Штатный запрос делается один раз на процесс (атомарный флаг):
два диска — один запрос.

Порядок на наблюдавшей нити: **латч → запрос остановки → строка `ERROR`**. Ошибка при построении
или записи строки не отменяет запрос. Для второго класса: латч → `LOG_FATAL` → `std::terminate()`.
Отдельной задачи нет; нить продления после запроса выходит из цикла без дальнейшей работы и
присоединяется в `stopBackgroundWorkers`.

Не `kill(0, SIGTERM)` (`SYSTEM SHUTDOWN`): тот бьёт по группе процессов, watchdog пересылает сигнал
серверу второй раз, и второй `SIGTERM` завершает процесс немедленно. При `kill(getpid(), …)`
watchdog не задет и ретранслирует код выхода ребёнка.

Что обещано для первого класса: немедленное закрытие допуска и запрос штатного завершения — не
мгновенный выход. Диск в `stopping` отклоняет новые изменения как повторяемую ошибку (проверка
частей не отсоединяет их во время shutdown), farewell не пишет, слив его ref-полосы запросов не
посылает. Код выхода — 0. `clickhouse-server.service` имеет `Restart=always`, `RestartSec=30`;
Kubernetes `StatefulSet` перезапускает по умолчанию (`Always`); при `Restart=on-failure` код 0
рестарта не даёт — это записано в документацию. `clickhouse-local` обработчика `SIGTERM` не ставит и
завершается сразу.

Проверяется процессным тестом с watchdog (`test_a_foreign_body_stops_the_server_under_the_watchdog`),
death-тестами колбэков по умолчанию, включая вызов из нити, блокирующей `SIGTERM`; юнит-тесты
классификации подменяют колбэки; тест для R17 инжектирует `NOT_IMPLEMENTED`, не `LOGICAL_ERROR` (под
debug и sanitizer тот — abort).

Старт при живом конкуренте: `claimMountAwaitingExpiry` наблюдает окно и возвращает
`LiveDoubleStart` → сервер не стартует → перезапуски повторяются. Это желаемый сигнал; строка
ошибки при старте называет конкурента.

Настройки для отключения остановки нет (решение владельца): процесс с закрытым диском проходит
liveness-пробы, и split-brain живёт, пока его не заметят по жалобам.

### Получение заново после фенса GC {#reacquire}

R8 значит: GC не видел продления дольше окна наблюдения и, сохранив наше тело,
поставил `gc_fenced`. Прежняя инкарнация отозвана; замена тела разрешена только по сертификату
(ETag прочитанного fenced-тела). Другой претендент мог успеть раньше — тогда таблица потерь.
Потребители `gc_fenced` сохраняют свои свойства. `isCreatorFenceTerminal` считает старый epoch
терминальным с момента фенса (`FenceCertificate::GcFenced`). Floor сборок (`floorForNamespace`,
`prefixEligibleUnder` в `CasOrphanManifestSweep.cpp`) берёт тело слота без проверки `gc_fenced`:
**до нового claim fenced-тело `(E, m)` продолжает защищать префиксы `(E, seq ≥ m)`** — это закрывает
гонку «sweep построил protection view → в полёте лёг ref-append старого epoch → sweep удалил его
манифесты»; после claim `E' > E` префиксы `E` становятся eligible. `closeOldEpoch` ждёт recovery
старого epoch и публикации снимков, но не append-лидера и не опустошения `active_build_seqs`:
`commitRefChunk` шлёт `op.create` без `state_mutex`, и отправленный ref-append старого epoch может
лечь после claim. Его манифесты защищает не `closeOldEpoch`, а поколение, `EpochSeal` и
`manifestDeletionPremise`: манифесты сборки удаляются только после свёрнутого курсора строго выше её
epoch, то есть после печати.

Нить продления выполняет два шага:

1. **Закрыть старый epoch** (`closeOldEpoch`): латч fence, `fence_generation + 1`, отмена
   recovery старого epoch и ожидание тишины (`cancelRecoveriesAndAwaitQuiescence`), сброс
   ref-таблиц (`quiesceRefTablesForRemount`). Всё это под старым `liveWriterEpoch` с латченным
   fence; `superseded_by_remount` и проверка поколения перед каждым durable-шагом — как сегодня.
   Это не farewell: `MountLeaseRenewer::release` на fenced-слоте не вызывается. Ожидания не видят
   stop; stop присоединяет нить после их завершения, как сегодня `FORGET`.
2. **Получить слот под новым epoch** (`claimNewEpoch`): identity probe, чтение каталога
   (`observe_catalog`, как в `tryRemountOnce`), `claimOwnerOrThrow` без права создать anchor,
   `allocateWriterEpoch` без права создать счётчик, `claimMount` в режиме `Reacquire` (возвращает
   наблюдение; классифицирует его тот же классификатор, что у продления), установка renewer от
   результата claim, `setLiveWriterEpoch`, продление до определённого исхода, если claim уже стар
   (ограниченное окно здесь не могло бы ни открыть запись, ни остановиться), открытие записи. Ref-таблицы перечитываются лениво; старая полоса запечатывается recovery
   нового epoch.

Правила:

- R19. Полномочия получения заново уже полномочий старта: ничего не создаётся — ни owner-anchor
  (`claimOwnerOrThrow` на пустом каталоге и поддереве данных сегодня создаёт его), ни счётчик
  epoch, ни слот. Отсутствие любого из них после подтверждения `LIST` — R16 (anchor, счётчик,
  каталог) или R13 (слот).
- R20. Режим `Reacquire` у `claimMount`: порядок проверок одного наблюдения — (1) байты равны
  текущей неизменяемой записи шага → шаг уже применён, продолжать; (2) `(наш uuid, старый активный
  epoch, gc_fenced)` и ETag равен сертификату → заменить; (3) GC-фенс нашего нового claim →
  получение начинается заново; (4) иначе таблица потерь тем же классификатором, что у продления
  (сравнение epoch раньше `gc_fenced` — его следствие; clean-marker fenced-пары — `slot_corrupt`).
  Clean-marker, `proven_dead`, `unsafe`-основания и `create` на этом пути не действуют.
- R21. Временный отказ любого шага (`503`, таймаут, `Refused`, `NotObserved`, `StayTransient`
  probe, временная ошибка чтения каталога) повторяется по R4 тем же кортежем. Шаг держит один
  небольшой объект: номер шага, выделенный epoch, сертификат. Каждая запись шага — одна
  неизменяемая условная операция движка, как продление (не `readModifyWrite`, который при
  конфликте решает заново внутри вызова): выделение epoch — `PUT` байт `{N + 1}` при ожидаемом ETag
  счётчика; неясный исход разрешается чтением внутри вызова. Счётчик, продвинутый кем-то другим
  (прочитано не `{N}` и не `{N + 1}` нашей записи), значит, что epoch этого `server_root_id` выделяет
  другой процесс — второй старт или декомиссия: остановка, `slot_taken`, со своим текстом
  («the writer epoch counter of this server_root_id was advanced by another process»). Исключительность новой инкарнации устанавливает условная запись слота по
  сертификату, не совпадение байт счётчика. Шаг, который уже применился, распознаётся по точным
  байтам.
- R22. Примитивы старта возвращают типизированные исходы, не текст исключения: `Replaced`,
  `IdentityLost`, owner tombstoned или чужой, счётчик отсутствует — R16; чтение каталога возвращает
  `Ok | Transient | Corrupt`: неоднозначный индекс жизней (`throwIfAmbiguous`) и недекодируемый
  каталог — `ledger_fault`, `Transient` — повтор.
- R23. Перед открытием записи под `driver_mutex` проверяются и латч завершения, поставленный с
  другой нити во время получения (R14, R18, stop), и дедлайн: решение и открытие — разные шаги,
  и между ними lease мог кончиться (модель показала `Live` без дедлайна при проверке одного латча).
  Побеждает первый терминал: потеря, наблюдённая после намерения `FORGET`, но до `closed`, — это
  `stopping`.
- R24. Ожидания тишины не имеют верхней границы и зависят от завершения чужих запросов
  (публикация снимка идёт обычным путём загрузки). Пока они идут — `paused` / `fenced_by_gc`.

Гарантия для операций старого epoch не меняется: операция, допущенная под старым поколением,
отказывает на следующем durable-шаге; `PUT`, уже отправленный, либо лёг законной записью старого
epoch, либо проигрывает `EpochSeal` (ref-журнал), либо становится мусором под старым epoch
(манифесты, precommit). Для каталога и plain-объектов — открытый аудит (раздел 10).

### Монотонность claim {#claim-monotonicity}

Отдельно от получения заново (PR 7): новая инкарнация не ставит epoch, меньший или равный epoch
заменяемого тела того же `uuid`, ни на старте, ни при декомиссии, ни в `Reacquire`. Задержавшийся
старт, прочитавший более новое тело, завершается ошибкой, а не заменяет его. При декодировании
счётчика epoch `next_writer_epoch = 0` отвергается. Пропуск номера epoch (неясный инкремент,
разрешённый чтением) безвреден: recovery ставит seal на каждый epoch ниже живого.

Над **отсутствующим** слотом заменять нечего, и правило выше ничего не запрещает: старт ставит
следующее значение счётчика, получение заново не ставит никогда (R13). Задержавшийся старт, чей слот
тем временем удалили (`SYSTEM CAS DROP POOL MEMBER` или руками), поэтому занимает слот заново.

Исходы на старте (PR 7): меньший epoch над более новым телом — `claimMount` бросает `ABORTED` сразу;
не-fenced тело той же пары — `LiveDoubleStart` с ранним выходом из `claimMountAwaitingExpiry`, без
записи и без окна наблюдения.

### Старт {#startup}

Поведение старта меняется в трёх местах: монотонность — строго больший epoch, поэтому ветка
`claimMount` «свой claim повторён — refresh» той же пары удаляется уже здесь: не-fenced тело той же
пары → `LiveDoubleStart` без записи (достижимо только при коллизии выделения — неясная непримененная
попытка одного старта и применённая другого дают один epoch; gtest-ы, вызывающие `claimMount`
дважды с тем же epoch, меняются) (PR 7); выделение epoch — та же неизменяемая операция, что при
получении заново, с двумя исходами для чужого продвижения счётчика — старт повторяет, `Reacquire`
останавливается (PR 11a); renewer строится от результата `claimMount` вместо повторного чтения и
записи слота в `MountLeaseRenewer::claim` (PR 11b).
`start_boot_ms` фиксируется **до** формирования тела логической claim-операции; все физические
повторы и чтение, выясняющее исход, сохраняют его; `Claimed` возвращает это тело, его подтверждённый
ETag и этот `start`. Дедлайн — `start + lease`, как в R5; установка renewer его не переносит. Если
claim подтвердился поздно и остатка не хватает, до открытия записи нужно продление. Старт по-прежнему получает
слот через `claimMountAwaitingExpiry` (farewell или `gc_fenced` — сразу, иначе окно наблюдения) и
сообщает готовность, когда подтверждённого lease хватает на запись; если claim уже стар, нить
продления делает одно продление синхронно до объявления готовности — с сегодняшним ограниченным
окном: отказ — отказ старта, старт при лежащем хранилище не висит. Что остаётся от диска при
неудаче старта — решение владельца, в списке отложенного.

### Shutdown {#shutdown}

Shutdown запрещает новые изменения, останавливает и присоединяет нить (дождавшись запроса в полёте;
после запроса остановки нить работы не делает), выполняет проверку тишины. Farewell (чистый маркер)
пишется, пока токен наш — и после истечения lease тоже: условная запись безопасна, precondition —
наш ETag, — и нет неясных отправленных запросов, незавершённых ref-полос и публикаций снимков в
полёте (PR 13). Farewell не пишется в `stopping` (с PR 12), в `closed` и после продления, которое
кончилось без подтверждённого lease. Farewell после истечения избавляет следующий старт от окна
наблюдения. Цена: если lease истёк и хранилище лежит, обычный shutdown тратит на попытку farewell до
`max(10 с, 2 × конверт + запас)` = 16 с на диск, и диски идут по очереди. Ожидание тишины перед
farewell верхней границы не имеет.

## 3. Наблюдатели {#observers}

Наблюдатели — перезапущенный сервер с тем же `server_root_id` (reclaim), GC (fencing, обычный
раунд и rebuild) и декомиссия. Reclaim и GC не сравнивают часы: каждый ждёт, пока токен слота не
меняется, считая от момента, когда он сам впервые его увидел, с допуском 5 % на разницу хода. Оба
берут порог из одной функции, `mountObservationThresholdMs`. Декомиссия (`SYSTEM CAS DROP POOL
MEMBER`) не ждёт: она принимает терминальное свидетельство (farewell, `gc_fenced`) или отказывает,
так что правило ожидания доходит до неё через фенс GC.

| Правило | Значение |
|---|---|
| длина lease держателя `L` | `max(свой cas_mount_lease_ms, объявленный)`; объявленный = `expires_at_ms − started_at_ms`, если разность положительна, иначе 0 (PR 2) |
| окно | `L + L/20 + шаг` |
| шаг | reclaim: половина собственного периода наблюдателя; GC: собственный период наблюдателя. Период держателя в чужое окно не входит |
| первое наблюдение датируется | reclaim: после чтения (уже так); GC: до PR 1 — до чтения. PR 1 исправляет оба вызова `computeHeartbeatFloor`, но дефект живой только в раунде: rebuild строит одноразовый `Gc` с пустым `mount_obs` и фенсить не может |
| после неудачного fence-out | новое решение датирует наблюдение заново; накопленное наблюдение не сбрасывается временной ошибкой чтения (PR 1) |

PR 2 — единственное изменение протокола наблюдателей. Ожидание только растёт, поэтому пути фенса не
добавляются, а смешанные версии безопасны в любом порядке; оговорка про наблюдателя без PR 2 — в
разделе «Настройки». Не смоделировано: держатель, меняющий lease между продлениями. Тело нового
продления объявляет новое значение; наблюдатели, видевшие старое тело, ждут по старому, пока не
увидят новый токен.

## 4. Срок запроса и отсутствие {#request-deadline}

**Конверт.** Сегодняшний «конверт» запроса (таймаут 5 с + 2 × лимит соединения 1 с = 7 с) не
ограничивает попытку по времени: таймауты действуют на одну операцию сокета и перезапускаются на
каждом `recv`/`send`; `PUT` с `Expect: 100-continue` может длиться 17 с, ответ по байту раз в 4 с —
сколько угодно, редиректы — до 11 запросов в одной попытке.

Два PR. 17b и 18 отложены решением владельца (2026-10-08); 17a — последний и необязательный:

- **17a** — движок запросов CAS передаёт абсолютный дедлайн попытки (`start + срок`) до API
  клиента; проверка остатка перед каждым запросом цикла редиректов и перед повторной подписью. Код
  CAS и `src/IO/S3`.
- **17b** — транспорт соблюдает дедлайн: HTTP-сессия обрезает каждый connect, send, receive
  остатком; ожидание клиентского ограничителя скорости ограничено остатком; имя
  `cas_request_deadline_ms`. Общий код (`base/poco`, `PocoHTTPClient`) — решение владельца о
  размещении.

Контракт после 17b:

| Ожидание | Входит в дедлайн |
|---|---|
| соединение, TLS, отправка, ожидание и чтение ответа | да |
| редиректы и повторная подпись в `S3::Client::doRequest` | да |
| клиентский ограничитель скорости | да |
| DNS (`getaddrinfo`) и получение учётных данных (STS, GCP OAuth, включая ожидание мьютекса) | время **учитывается** общим дедлайном (остаток проверяется до и после, превышение завершает попытку; новых пяти секунд после DNS нет), но сами вызовы **не прерываются** |

Поэтому срок запроса описан как срок **сетевой части** попытки, неограниченная попытка после 17b
закрыта частично, и в арифметике допуска значение срока используется только после PR 18, который
идёт после аудита.
Полная попытка остаётся неограниченной и после 17b (DNS, учётные данные не прерываются).

**Отсутствие.** `ProvenAbsent` — это `GET` ответил `404` (с именем `NoSuchKey` или без) **и**
`LIST` префикса ключа не содержит ключа. `LIST`, который не удался или сам ответил `404`, даёт
`NotObserved`: остановки нет, фоновое продление читает снова. Требований к телу ответа `404` и к
бакету нет. `LIST` спрашивается только перед терминальным решением: `slot_absent`,
`pool_identity_lost`, отсутствие anchor, счётчика или каталога при получении заново (PR 12, PR 14).
До PR 12 отсутствие owner, каталога и счётчика решается одним `GET` (PR 11a, 11b).

Базовые факты, на которые опирается правило: `isObjectNotFound` (`CA/Backend/CasObjectStorageBackend.cpp`)
считает отсутствием любой `RESOURCE_NOT_FOUND`, включая `404` без имени ошибки; отсутствие при `HEAD`
решают `S3::getObjectInfoIfExists` и `isNotFoundError` (туда же попадает `NO_SUCH_BUCKET`); `stream`
— тоже `GET`. Прокси или запрос, ушедший не туда, отвечает `404` так же, как хранилище; поэтому один
`GET` ничего не доказывает. Отличать отсутствие по глаголу и по имени ошибки серия не стала (раздел
11). Не-S3 бэкенды (локальный, эмулированный): `FILE_DOESNT_EXIST` остаётся отсутствием.

## 6. Что не меняется {#unchanged}

- Формат объектов в хранилище. Наблюдатели меняются только в PR 2, и только в сторону более долгого
  ожидания.
- Протокол ref-журнала, `EpochSeal`, разрешение неясных append, wedged-полосы. Выход из
  `NeedsRecovery` без remount на базе есть (`needs_rerecovery` при следующем обращении,
  `ensureRefTableRecovered`); PR 10 его проверяет тестом сохранения поведения. Wedged-полоса без
  следующей мутации остаётся wedged и блокирует farewell и публикацию снимка — цена сегодняшнего
  протокола, отдельная задача.
- Глобальное лидерство GC (`gc/state`, `gc/hb`): потеря mount lease не трогает местный GC;
  потеря лидерства GC не трогает запись (отдельная задача).
- Правила декомиссии, кроме двух: её фоновое продление с PR 8 тоже идёт до определённого исхода;
  потеря её claim с PR 12 завершает команду ошибкой (раздел «Потеря»).
- `cas_unsafe_remount_no_delay` на старте; поведение старта (кроме раздела «Старт»).
- Значения по умолчанию всех настроек.
- Резерв допуска записи и его две категории (раздел 1) — до PR 18; заданный
  `cas_lease_safety_margin_ms` учитывается и после PR 18.

второе выделение или claim посреди первого, продлевать посреди получения заново и т. п.; продукт
исключает это тем, что нить одна. Каждый такой guard введён по контрпримеру TLC и действует только
в конфигурациях со своим флагом.

## 10. Безопасность {#safety}

Проверка допуска (доказуемая): операция начинается только если по расчёту бюджета до конца lease
остаётся больше её резерва; истёкший lease не даёт права писать. Предел завершения
(недоказанный): «попытка заканчивается за один конверт» — допущение; без 17b не ограничена и сетевая
часть попытки. Завершение необратимо: латч до любого действия. Фенс стоит epoch; сертификат привязан
к конкретному телу и его авторству. Наблюдатель не сравнивает часы и ждёт не меньше объявленного
lease.

Предпосылки целостности пула, которые серия не проверяет:

- Объект счётчика epoch не теряется, пока существует слот или данные этого `server_root_id`. Если
  он пропал между выделением одного старта и его claim при отсутствующем слоте и пустом поддереве,
  два старта получают один epoch и оба могут писать.
- Часы хода: держатель, у которого `CLOCK_BOOTTIME` стоит, пока часы наблюдателя идут (остановленная
  виртуальная машина), — вне допущения 5 %.

Что не доказано и не меняется в серии до аудита:

- Поздняя запись вне ref-журнала. `casPutObject` / `casRemoveObject` проверяют ETag своего
  объекта, а не epoch mount; преемник может сменить mount, не тронув этот объект, и ранее
  отправленная мутация применится. `ObjectStorageBackend::publish` идёт обычным путём загрузки.
  Серия не расширяет этот риск: резерв сохраняется до PR 18, PR 18 — после аудита всех
  durable-шагов (каталог, манифесты, precommit, plain-объекты) и модели поздних эффектов.
- Отставшее продление. Запрос продления, отправленный до выделения нового epoch, может лечь после
  него; рядом с счётчиком `N + 1` окажется живое тело epoch `N`. Данных это не портит: латч записи
  стоит до выделения и не снимается до нового claim. Цена — одно окно наблюдения. В получении
  заново (PR 14) нить сначала разрешает свою операцию продления, потом закрывает epoch.
- Ворота свергнутой полосы в `flushRefBatch` могут сработать, если flush-лидер вытеснен на всё время
  получения заново. После PR 15 окно уже, но осталось; моделью не покрыто.

Не смоделировано: держатель, меняющий lease между продлениями; `LIST`, идущий наперегонки с
удалением или claim; несколько GC-лидеров одновременно.

## 11. Отклонённые варианты {#rejected}

| Вариант | Почему нет |
|---|---|
| Рестарт процесса после любой потери, включая `gc_fenced` | сбой дольше окна наблюдения требовал бы рестарта; не нужно: fenced-тело своё, замена идёт по сертификату |
| Закрыть монтирование, сервер работает (`restart_required`, gauge) | решение владельца: процесс с закрытым диском проходит liveness-пробы; split-brain виден только по жалобам |
| Одна реакция на все потери (`SIGTERM`) | shutdown пишет farewell и закрывает `_ckpt`; при нарушенном инварианте процесса это запись под чужой, возможно, идентичностью. Поэтому два класса (предварительно) |
| `raise(SIGTERM)` с наблюдавшей нити | нити Poco блокируют `SIGTERM`; сигнал нити остаётся висеть. Нужен сигнал процессу: `kill(getpid(), SIGTERM)` |
| Автоматически ждать ухода конкурента и забирать слот | качели владения; дубликат `server_root_id` не выявляется |
| Получение заново для отсутствующего слота, anchor или счётчика | воскрешает участника, удалённого декомиссией |
| Отсутствие по глаголу (`GET` — только `NoSuchKey`) | хранилища, отвечающие `404` без имени или `NotFound`, не смонтировали бы пустой пул; upstream принимает оба ответа. Вместо этого `LIST`-подтверждение перед терминальным решением |
| Типизированные причины ошибки ref-полосы (`interference` / `corrupt` / `defect`) | реакция одна; три пути отчёта без разного поведения. Сырые факты идут в сообщение |
| Ветка «лимит памяти → повторить позже» в коммите ref-полосы | лишний путь; guard `LockMemoryExceptionInThread(Global)` на всём пути коммита убирает сам случай |
| Один `cas_tick_ms` и всё в тиках | связывает срок запроса с длиной lease; срок запроса зависит от расстояния до хранилища, длина lease — от допустимого простоя |
| `cas_mount_write_pause_after_ms` как главная настройка | lease = пауза + резерв: изменение локального срока запроса меняло бы lease |
| Период как треть lease по умолчанию; игнорирование заданного запаса | сегодня период по умолчанию 10 с при любом lease; выведенный период отверг бы работающие конфигурации с другим lease; игнорирование запаса меняло бы резерв. Ничего не выводится и не игнорируется |
| Объявленный lease с верхней границей (cap) | дефектом был именно cap: он отзывал действующего держателя с длинным lease. `max` без cap не добавляет пути фенса — ожидание только растёт |
| Резерв на стороне наблюдателя | меняет протокол; наблюдатель должен знать чужие бюджеты запросов |
| Резерв в один запрос | неясный `PUT` у границы wedge-ит полосу; отложено вместе с 17b и аудитом |
| Настраиваемая остановка сервера | fail-close по умолчанию; выключатель — приглашение оставить split-brain |
| Остановка отдельной задачей | отказ диспетчера оставил бы живой split-brain; запрос с наблюдавшей нити безопасен |
| Сравнение авторства по байтам | заморозило бы набор полей `MountLease` для всех GC-бинарников; сравниваются декодированные поля |
| Удалить `cas_unsafe_remount_no_delay` | это настройка старта после `kill -9`, не remount |
| Отдельный PR для значений по умолчанию | две строки без замеров; вне серии |
| Правило «1–3 теста на PR» | ограничивать нужно тему; таблица потерь требует тест на каждую строку |
